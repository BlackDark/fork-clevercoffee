# Findings of 2026-10-03 — independent review of the Rust port

An outside review of the migration, run against `rewrite/rust` with the migration documents
treated as **untrusted claims** rather than as the specification. Every claim below was checked
against the code in `crates/` and the C++ oracle in `src/` + `include/`, not against
[`target-architecture.md`](./target-architecture.md) or
[`divergences.md`](./divergences.md).

Read this after [`31-findings-2026-10-01.md`](../archive/migration/31-findings-2026-10-01.md), which indexes the
port's own session findings. This file indexes what an independent pass found that was not in it.

Status vocabulary matches that file: **fixed**, **reported**, **open**.

---

## Summary

The **architecture holds**. The portable/device boundary is real and CI-enforced, not conventional:
`scripts/portable-purity.py` strips comments and strings and fails the build if any
`esp_idf_{hal,svc,sys}` reaches the five portable crates' *code*. There are zero leaks in code.

**Build and test speed needs no work.** Measured on a 3-core machine:

| gate | wall clock |
| --- | --- |
| `cargo fmt --all --check` | 0.4 s |
| `cargo clippy --all-targets` (host crates) | 3.7 s |
| `just check` (host: fmt, clippy, rustdoc, ~1,349 tests, parity, audit) | 9.4 s |
| `just check` from a cold target dir | 12.8 s |
| `just gate` (adds device clippy, Xtensa release build, size budget) | 18.8 s |
| `just build-esp32` (warm) | 15 s |

Note `just check` does **not** compile `cc-hal-esp32` or `cc-firmware`. Any change inside those
crates needs `just gate` (or at minimum `just lint-esp32` + `just build-esp32`) to be verified.

**Four defects were confirmed, two of them safety-critical, and all four are fixed.** Section 1.

The fixes are four commits on `rewrite/rust`, each gated on `just gate`:

| commit | defect | where the rule now lives |
| --- | --- | --- |
| `3794bef6` | 1.1 dead probe | `TemperatureSensor::has_error()` ORed into the sample |
| `ee717438` | 1.2 setpoint bound | `cc_safety::validate_config` (the brew pair) + `assign::parse` (the write) |
| `44c546db` | 2.1 snapshot read | `Snapshot::get` restores inside the same critical section |
| `55f92c5b` | 2.2 brew weight | `scale_weight()` at SENSE + `validate_config` refusal |

A later commit fixed **2.3, 2.4 and 2.8** together, because all three are the same class of defect:
a relationship 04 §2 or `pinmapping.h` states as a table that nothing in the code establishes.

| defect | what now establishes it |
| --- | --- |
| 2.3 task priorities | `task::spawn_with_prio`, with the 5/3/4 ordering asserted by a `const _` |
| 2.4 pin map | `pins::assert_valid` (a `const fn`, so a bad pin is a **build** failure) and `pins::assert_wiring` (boot-time, because `esp-idf-hal` 0.47 reaches a pin's number only through a non-`const fn` and offers no safe way back) |
| 2.8 staged parameters | `ParameterHandoff::take_one`, one request per tick, with the ack staying 1:1 |

Three of the four were fixed at a **shared invariant rather than at the write path**, which is why
they cover every writer (HTTP, MQTT, `/api/parameters`, NVS) instead of only the route where the bug
was found. `validate_config` grew from four inputs to nine; the doc comment at `cc-safety/src/lib.rs`
records the rule for that set ("every field is one somebody had to think about").

## 1. Safety — fix before the firmware energises a boiler

| # | finding | severity | status | where |
| --- | --- | --- | --- | --- |
| 1.1 | **A failed temperature probe is invisible to the state machine, and the PID then regulates against a frozen reading forever.** `has_temperature_error` is derived from the *cached* `last_reading`, which `TemperatureSensor::poll` never invalidates on a fault. `Ds18b20Driver::has_error()` latches correctly at 10 bad reads and had **zero callers outside its own unit tests**. The C++ reaches `SENSOR_ERROR` via `TempSensor::error_`. `sample_seq` deliberately still does *not* advance on a fault: it counts completed conversions, and advancing it would let the over-temp debounce trip on a number nothing is producing. | P0, can-damage | **fixed** | `cc-firmware/src/main.rs:2793` |
| 1.2 | **`POST /api/setpoint` bypassed the schema bound and persisted the result, defeating the over-temperature interlock.** The handler filters `0..=150`; the write path skipped `cc_config::assign::parse` and persisted directly, while the schema bound is `20..=110`. `emergency_temp` defaults to 150 and S1's test is *strictly greater*, so a 150 °C setpoint means the debounce can never trip. `validate_config` compared only the *steam* pair, and `BlobConfigStore::load` did not re-validate. The C++ cannot reach this because `ParamDef::set` range-checks the same write. Fixed as `intentional-diffs` §23; the brew pair is compared against the **effective** setpoint, so `brew.temp_offset` (bounded 0..=20) is carried in `SafetyConfig` too. | P1, can-damage | **fixed** | `cc-web/src/request.rs` (`parse_setpoint`), `cc-safety/src/lib.rs:953` |

## 4A. Finding 4.1 — the fix, and the two claims in it that were wrong

`cc-web` is the sixth portable crate: `#![no_std]` + `alloc`, depending on
`cc-domain` and `cc-config` (plus `heapless` and `log`, both already in the graph
and both needed for reasons the crate's `Cargo.toml` states). It is in
`default-members`, in the justfile's `host_crates`, and in
`scripts/portable-purity.py`'s `PORTABLE` — the last one is the point: the whole
value of the crate is that `just test` can reach it, and a purity list that did
not name it would leave that unenforced.

`web.rs` went from 4,669 to 3,579 lines. What stayed is route registration,
`respond`/`respond_large`/`respond_download`, the SSE broadcaster and its
`web_async` seam, `routes()`, `resolve_ui` + the embedded bundle, `history_json`
(it takes `&Shared`), the httpd `Configuration`, and `Shared`/`Snapshot`. What
moved is `Telemetry`, `Command`, `Auth`, every `*_json` renderer except
`history_json`, `mime_for`, `ParameterPost`, `classify_parameters`, `needs_reboot`,
the three request limits, and the five request-parsing helpers.

**46 of `web.rs`'s 71 device-only tests are now host tests**, and
`device_tests::CASES` shrank by the same 46 (169 → 123). Image size is unchanged
within noise: 1,664,672 → 1,664,848 B, growth 6.74% → 6.75% against a 10% limit.

### `Snapshot`: option (b), and it was free

The finding says `Snapshot` "cannot" move and asks for the payload to be separated
from the primitive. **It was already separated.** `Snapshot<T>` is generic over
its payload; only `Telemetry` moved, and `Snapshot<cc_web::Telemetry>` type-checks
with no change to the type, to its hand-written `Sync`, or to commit `44c546db`'s
take-and-restore inside one `interrupt::free`. The critical section was not
widened, the read was not made non-atomic, and the `unsafe` stayed next to the
argument that justifies it.

The alternative — a portable `Snapshot` over a host primitive — would have needed
either a trait with one implementation or a `Sync` impl whose safety argument no
longer held. Neither is worth the appearance of portability.

### Two claims in the finding are wrong

1. **"`Telemetry`, `Command`, `Snapshot`, `Auth`, every `*_json` renderer,
   `classify_parameters`, `resolve_ui`, `mime_for` and the route table are pure
   functions of a `Config` and a snapshot."** Four of them are not, and stayed:
   * `Snapshot` (uses `interrupt::free`) — the subject above;
   * `resolve_ui` reads the asset table `build.rs` generates from the Vite
     output, so it is a build-time product, not a value;
   * `routes()` returns `esp_idf_svc::http::Method`, so the route table *is* a
     statement about what ESP-IDF registers.

   And two renderers were impure for a smaller reason: `status_json`
   interpolates `free_heap()` and `nvs_debug_json` interpolates `free_heap()`
   and `min_free_heap()`. Both are `esp_get_free_heap_size()` FFI reads. They take
   the readings as arguments now; **the bytes they emit are unchanged** and the
   caller passes the same gauge at the same point.

2. **"depending only on `cc-domain` + `cc-config`."** `Telemetry::ip` is a
   `heapless::String<15>` and must stay one — it is what makes a reader's copy a
   `memcpy` with no allocator traffic, which is the whole `Sync` argument — so
   `heapless` is a dependency. `Auth::from_config` reproduces the C++'s loud
   `LOG(WARNING)` when authentication is enabled with no credentials, so `log` is
   one too. Both crates were already in the graph (`cc-machine` uses `heapless`
   for `Effect`); neither adds a download to any build.

### A third broken test, found by the move

`the_status_steam_mode_agrees_with_the_steam_toggle_response` asserted that
`status_json` contains `{"success":true,"steamMode":…}`. `/api/status` has never
emitted a `success` key, so the test could only ever fail — and it did not fail
on hardware, because `cc-hal-esp32` is unreachable from `cargo test` and
`just test-esp32` is not in `just gate`. This is the first instance of the gap
that is a *broken test* rather than an untested bug. The assertion is now on the
field both documents actually carry.

### What was NOT done here

**`mqtt.rs` was untouched by this step**, and that is what the half-done
extraction claim in 4.1 refers to. Its pure half moved later, as its own commit;
see §4A2 below. Findings 4.4 and 4.7 are still untouched.

## 4A2. Finding 4.1b — `cc-mqtt`, the same extraction for MQTT

`cc-mqtt` is the seventh portable crate: `#![no_std]` + `alloc`, depending on
`cc-domain` and `cc-config` (plus `heapless` and `log`, both already in the
graph, both for the reasons its `Cargo.toml` states), in `default-members`, in
the justfile's `host_crates` and in `scripts/portable-purity.py`'s `PORTABLE`.

`mqtt.rs` went from 2,033 to 875 lines. Moved: `Topics`, `ParamTopic` and the
four machine-state constants, `Registry` and its `from_config`, `PlanView`,
`Payload`, `SetCommand`, the intervals, the buffer sizes and the two
size bounds, `interval_for` and `is_configured`. Stayed: `Client`, `Link`,
`note_event_on`, `receive`, `Feed`, `Service` and the two `esp-mqtt` task
constants. The HAL **re-exports** everything that moved, so `cc-firmware`'s
`mqtt_link` and every `cc_hal_esp32::mqtt::` path in prose are unchanged by the
move.

**All 19 of `mqtt.rs`'s device-only tests are now host tests**, and
`device_tests::CASES` shrank by the same 19 (128 → 109). Host test count
1,172 → 1,191. Image size 1,675,920 B, growth 7.34 % → 7.46 % against a 10 %
limit.

### The purity check came back cleaner than the `cc-web` one

`cc-web`'s extraction found three things its brief had called pure and were not:
two renderers interpolating `free_heap()`, a `history_json` that took `&Shared`,
and two dependencies the brief had not named. **`mqtt.rs` had none of the
first**, which is the interesting result: `esp_get_free_heap_size()` appears
nowhere in it, and neither do `now_ms()` or a free-running tick outside the
publisher. Every MQTT item is a function of a `Config` and a `MachineState`.

The dependencies trap did recur — `heapless` (`Payload`, `SetCommand`) and `log`
(the two overflow `warn!`s) are both needed, and both were already in the graph.

`receive` is the one judgement call: it is the C++'s
`MQTTManager::messageCallback` (`MQTTManager.cpp:237-274`) and it is **not** pure,
because it locks the inbound queue. Its *parse* is pure and moved with
`Topics::command_of`, so the `%119[^\/]` matcher is host-tested from `cc-mqtt`;
the queue push stayed. Splitting `receive` itself would have been a restructure
with no test to justify it.

### Two visibility widenings the boundary forced, and why

`Payload::overwrite` and `PlanView::items` were private. They cannot stay that
way across a crate boundary: `Feed::remember` (which stayed, in the HAL) stores a
`Payload` per topic, and `a_registry_never_names_a_credential` reads the
flattened items to assert that no topic carries the broker password. The first is
now `pub`, the second `pub(crate)`. Both are the same reach the tests already
had; neither widens what a caller can do.

## 4B. Finding 4.2 — measured, and the fix was to the rule, not to the code

**The finding was right that code and stated rule disagreed, and wrong about
which of the three mattered.** Measured 2026-10-04; the rule is amended in
`crates/cc-firmware/src/slots.rs` and in 04 §3.2, and **no lock was changed**.

### The numbers

Sizes are `size_of`; hold times are the host microbenchmark of the identical
loop, scaled to 240 MHz at **8× pessimism**. No Xtensa figure is a device
measurement — measuring one means flashing, which the migration forbids — so
each is a deliberately generous upper bound rather than a guess.

| lock | guarded value | control-side hold | holder-side hold | taken |
| --- | --- | --- | --- | --- |
| `ParameterHandoff::take_one` | `VecDeque` of 4 `Vec` fat pointers, pairs on the heap | `pop_front`, 12 B: **<= 0.04 us** | `len` + `push_back`: **<= 0.5 us** | every tick |
| `network::Handoff::take` | `Option<Staged>`; both `String` bodies on the heap | `Option::take`, <= 28 B: **<= 0.1 us** | `is_some` + 28 B store | every tick |
| `Shared::push_history` | `Box<History>`, 600 × 12 B = 7,200 B | one 12 B point store: **< 0.01 us** | 7,200 B copy-out: **<= 22 us** | **1 Hz** |

The priorities are what settle the rule's second half. httpd is at **5** —
level with control, because `esp-idf-svc-0.53.0/src/http/server.rs:161` writes
`task_priority: 5` as a literal and `Configuration` exposes no field to change
it. So none of the three is an inversion, and priority inheritance is a no-op
on them. provisioning (4) is the only lower holder and it inherits to 5 and
releases at once.

### What the numbers changed

1. **`push_history` is not per-tick.** It sits inside the `SSE_INTERVAL_MS`
   gate (1000 ms, the C++'s `sendTempEvent` cadence), so it is one lock per
   *second*, not one per 10 ms period. The finding's own framing counted it as
   one of three per-tick locks; it is one in a hundred.
2. **The two genuine per-tick locks are unremarkable.** Sub-microsecond on both
   sides. They cannot be what makes the loop miss its period.
3. **The 7 KB figure is real, and bounded.** 225 cold 32-byte DRAM lines at a
   pessimistic 100 ns each is <= 22 us — 0.2 % of one tick, once a second, and
   only while a browser is on `/api/history`. It is not 7 KB of memcpy *per
   tick*; it is 7 KB once a second behind a rare request.
4. **The worst case is the scheduler, not the section.** `configUSE_TIME_SLICING`
   is 1 and `CONFIG_FREERTOS_HZ` is 100, so an equal-priority switch lands on
   the 10 ms tick: a colliding tick waits for the rest of the section *and* for
   httpd to block. Collision probability is hold-over-period, **~5e-5 per tick**
   for the mailbox. And step 9 sleeps
   `CONTROL_PERIOD_MS.saturating_sub(elapsed)`, so a lost tick is absorbed
   rather than accumulated.

### Why no refactor

A `Cell` under `interrupt::free`, or a double buffer published by pointer swap,
would each replace a section already bounded at <= 22 us with **a second
synchronisation object**, and the swap variant puts the 7,200 B on the control
side — the direction the numbers say is the cheap one. A cell was also
explicitly ruled out by the task's own risk note: 7 KB inside
`portENTER_CRITICAL` is a 7 KB interrupt-disabled window on a chip whose S1-S5
safety paths run inside that window. Deletion over addition: the mutex stays.

### What was deliberately not changed

- **The `stage_and_wait` protocol** (Release/Acquire, wrapping-safe timeout) is
  intact and untouched. It was re-read, not weakened.
- **Nothing on the httpd side.** Not one line of `web.rs` or `history_json`.
- **The findings' line numbers** (`main.rs:2550,2629,3185`) are stale — the sites
  are `main.rs:2714`, `2794` and `3432`. Recorded here rather than edited into
  the table.

### What remains unverifiable, and is not claimed

Whether a contended `std::sync::Mutex` **between these two tasks** can trip the
`xTaskRemoveFromEventList` assert. The assert reproduced against
`interrupt::free` from a second task and against three blocking wake primitives
(09 §28); the mutex path was not isolated, because isolating it means flashing.
What is established is that these three locks have run contended on the device
through every 10 ms-loop build.

## 5. Divergences from the plan that are **better** — protect these

`target-architecture.md` is not always the target. Seven places where the code improved on the plan,
recorded so nobody "fixes" them back:

1. The `TemperatureProbe` trait was **deleted** rather than built on spec — a trait with no
   implementors is worse than no trait, and `sensor/mod.rs` was corrected to stop claiming
   `cc-machine` takes a `&mut dyn TemperatureProbe`.
2. **No `Clock` trait.** `Event::Tick { now }` carries the reading instead, which is precisely what
   makes `reduce` pure.
3. **`Effects` is a `heapless::Vec<Effect, 32>`**, gated by an allocation test — inline, no heap.
4. **`cc-provisioning` was deleted** rather than left as a skeleton (§6 sanctioned this).
5. **`cc-device-tests` and `cc-parity`** exist as out-of-`default-members` tools and are not in the
   plan at all. Both earn their place.
6. **`water_flow_allowed` / `steam_flow_allowed` are `match` with no `_` arm**, so a 19th state cannot
   compile without being classified.
7. **There is no `Board` trait, and there is not going to be one** (finding 2.4). `04 §1.4` and
   §6 promised one to make the pin map validated. The machine is one board, so a trait with one
   implementation is a `const` map plus a name; what was missing was the *validation*, and
   `cc_hal_esp32::pins::assert_valid` — a `const fn`, so a bad pin is a build failure — supplies
   exactly that without the indirection.

The stack choice is also correct and current: **ESP-IDF Rust** (`esp-idf-svc`), not bare-metal
`esp-hal`. `esp-hal` 1.0's WiFi/BLE on the original ESP32 is still behind an `unstable` feature and
has no NVS, HTTP or MQTT story at all. `std::thread` (a thin FreeRTOS wrapper in the ESP-IDF std port)
is the right concurrency model here; embassy is an `esp-hal` story and would be a regression. The
`esp-idf-*` crates are community-maintained with little paid Espressif support — worth knowing, but
the alternative has none of the services this firmware needs.

## 6. Verified sound — do not "fix" these

- **The PID port.** A deliberately careful transcription: the clamp reproduces the C++'s `if/else if`
  chain so a `NaN` passes through rather than being snapped, and the doc explains why `f64::clamp`
  would be wrong. The `SampleTime / 1000` integer-division trap is closed with a real-time divisor,
  with the trap left visible in `derivative_seconds()`. Anti-windup, integrator limits, bumpless
  transfer and negative-gain rejection all match `PID_v1.cpp`.
- **The heater path.** `HeaterGate` has no armed constructor — the only way to open it is a heartbeat
  — and gating runs *last*, after quantisation, so a stale-high permit is impossible.
  `AtomicChopper::tick` is integer-only, which is a hard requirement on Xtensa (an FPU instruction in
  a level-1 ISR is a fatal coprocessor exception), and is exhaustively proven equivalent to the `f32`
  reference over 1001 × 103 inputs.
- **Concurrency primitives.** Both prior seqlocks were correctly identified as unsound and replaced
  with `interrupt::free` critical sections; the `unsafe impl Sync` blocks state their invariants as
  grep-checkable facts. `ParameterHandoff` uses `Release`/`Acquire` correctly with a wrapping-safe
  ack timeout.
- **State-machine flag hygiene.** `clear_all` / `clear_stale_stops` model the C++'s two drain helpers
  as operations on the group, so a new flag cannot be added without being covered.
- **Effect-list overflow** is counted, not panicked, with an exhaustive host test pinning
  `dropped() == 0` across all 4,140 state × event pairs.
- **The boot readback** asserts every actuator pin inactive before anything else exists, and the
  heater ISR is armed only after the first supervisor beat.

### 9.1 — the display allocation gate counted the harness, not the frame

`crates/cc-display/tests/frame_allocations.rs` — `a_frame_does_not_allocate` failed **3 of 12 runs
under artificial CPU load and 0 of 30 idle**. The failure message is
`rendering 60 frames allocated 4 times (900 bytes)`, i.e. the gate was measuring
something other than the frame.

**Cause: found and fixed.** The counters in `crates/cc-display/benches/alloc.rs` were process-global
`AtomicU64` with `Relaxed` ordering. A `#[global_allocator]` is invoked for allocations anywhere in
the process, and libtest runs the test body on one thread while the harness keeps working on the
main thread — so any harness allocation inside the window was attributed to the frame. This is the
same hazard the sibling gate documents for itself (`tick_allocations.rs`, lines 12-23: *"a
measurement that counts the harness is not a measurement of the reducer"*), which had previously hit
it from a `Box::leak` in its own window.

Instrumenting the allocator to print the thread id of every allocation inside the window settled it:

| size/align | allocating thread | site |
| --- | --- | --- |
| — | `ThreadId(2)` | the test body, i.e. `cc-display` — nothing |
| 148 / 16 | `ThreadId(1)` | `test::term::termininfo` capability `HashMap` |
| 608 / 8 | `ThreadId(1)` | `VecDeque<TimeoutEntry>::push_back` in `test::run_tests` |
| 48 / 8 | `ThreadId(1)` | `run_test` — `Box<ArcInner<Packet<()>>>` for the spawn |
| 96 / 8 | `ThreadId(1)` | `run_test` — `Box` for the spawn closure |

**`cc-display` allocated nothing.** All four bytes are the harness, on the other thread.

**Fix: the counters are thread-local** (`benches/alloc.rs`, both crates' copies kept identical).
This is not a loosened threshold — `assert_eq!(allocs, 0)` is unchanged and still fails on the
first heap byte the rendering thread touches. `templates::render` is single-threaded and runs
entirely on the display task on the device, so the rendering thread is the only one that can
allocate on a frame's behalf. Measured on the same 32-spinner load: **62 of 80** failures before,
**0 of 80** after. (The rate is load-sensitive: 1 of 20 in a lighter session, 0 of 30 idle. The
load, not the code, is what sets the rate — which is exactly why it read as an intermittent flake
rather than a constant failure.) With `--test-threads=1`, which puts the harness on the test's own
thread and removes the interleaving that hid the race: 22 of 40 before, **0 of 40** after.

The same one-line change covers `cc-machine`'s identical copy, so its gate is no longer exposed to
the class of failure its own header describes.

**A hypothesis that was tested and WRONG.** The test warms up by rendering `TemplateId::Standard`
once, then renders all six templates — so five templates' first-render cost is inside the measured
window. Widening the warm-up to all six templates looked like the fix. It is not: with the change,
**0 of 30** failed, and with the original restored, **0 of 30** also failed. The warm-up is not the
cause. Recording this because the hypothesis is the obvious one and it would have looked like a fix.

**Why it mattered.** This is a gate in `just check`, and CI runs it. A gate that fails ~25 % of the
time under load trains people to re-run until green, which is exactly how a real allocation gets
merged.

**Status: fixed**, at the allocator rather than at the call site, so both gates inherit it. Loosening
the threshold was never an option — it would weaken a real invariant that `cc-display`'s
`no_std`-without-`alloc` design depends on.

### Why `pump` went rather than stayed with a banner

The stated reason for keeping it was that it is "staged for the R3-16 transport".
That reason does not survive contact with the oracle: **the C++'s `Logger` never
reads a line from a telnet client.** `Logger::update` (`src/Logger.cpp:123-156`)
accepts a client, writes the banner, flushes the ring and pumps the heartbeat —
and `rg 'client_\.'` over the file finds only `write`, `flush`, `stop` and
`connected`. `pump` was therefore not staged parity work; it was a *read* path
with no C++ to match, and its own doc claimed a `Logger::update` shape
(`accepts a new client, welcomes it, and pumps the heartbeat`) that the C++ has in
the *other* direction only. `LineBuffer` existed solely to feed it.

The counter-argument — staged work is worth keeping — is real but it is a
question of *what* is staged, and this was a guess wearing a C++ citation. The
repo has already taken the other side of this trade once, on the same grounds and
with the same reasoning recorded: the `LedcPwm` transport, ~190 lines, zero
construction sites, deleted (`divergences.md`, "What is kept and what is
dead"). The rule this repository applies is that a staged feature needs a named
consumer, and an unreachable `pub` in a firmware image is maintenance cost with
no offsetting asset — it cannot be exercised by `just test`, it cannot be
exercised by `just test-esp32` without a device, and its "why it exists" comment
is the only thing keeping it alive.

What survives is the part that is a fact about the C++: the 256 B line bound
(ADR-0002 decision 1) and the shed policy both stay, and the former is still
reachable — `web.rs`'s `drain_body_bounded` uses `LINE_BUFFER_BYTES`, so the
constant outlived its type.
