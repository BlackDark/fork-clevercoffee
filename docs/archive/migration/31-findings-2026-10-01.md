## 7. Still open, with the next step named

1. **The control tick runs at ~65 Hz, not 100 Hz.** Measured: the **applier span**
   is 12 ms of the 15; sensors, reducer and display are all 0 ms. Nothing in that
   span obviously blocks. **Next:** split it into `apply` / `drain_scale` / the
   reboot checks and read the same line. (`09-cpp-findings.md` §31)
2. **`CONFIG_FREERTOS_HZ`** was raised to 1000 and reverted — identical numbers, so
   the tick rate was never the limiter. Revisit only if (1) lands under 1 ms.
   (`09-cpp-findings.md` §29)
3. **Text that overflows its slot** (3.6) and **the 1 px message overlap** (3.7) —
   both need a product decision about typography. `profont10` for the message
   screens is the cheapest fix and changes six screens.
4. **A gate does not fail on a LOST device test** (6.2).
5. **`POST /api/parameters` and the other mutating routes answer before the
   machine has acted** on a value they persist. The write path is fixed; the
   "reboot required" answers are honest, but a general read-after-write contract
   is not.

## 8. What this session got wrong, on the record

Three of these cost hours and are worth more than the fixes:

* **A layout "fix" computed from `str_width` instead of `ink_box`** — done once,
  believed fixed, and wrong. The second time, the log said `deciding` *and* `acting`
  were both 12 ms, which is what gave it away.
* **`testnet` read as an encryption problem** for most of a day, because the log
  said "the configured network is unavailable" and stopped there. One length-only
  log line would have ended it in ten minutes; it did not exist.
* **A gate that was failing, committed and pushed anyway**, because the commit
  message had already been written asserting it passed. The lint was
  `missing_errors_doc` on a function I had just moved.
