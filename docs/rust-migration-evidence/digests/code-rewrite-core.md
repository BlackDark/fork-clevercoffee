A note on the "pinned by" column, which is the whole point of this pass: this corpus uses
two naming conventions and they encode review status.

- `s<N>_…` — a **C++ defect reproduced on purpose**, pinned so a silent "fix" would show up in the diff.
- `div<N>_…` — a **deliberate divergence**, the human-approved departure from the C++.
- anything else — a host test of *this* implementation's behaviour, not a parity claim.
- no test at all — comment-only knowledge, at risk of being re-broken.

## 4. Decisions reversed or corrected during implementation

What the code does that a first reading of the design docs would not predict.

- **The heater output method is not what R1-07 asked for.** R1-07 says 100 Hz; the code ships 1 Hz, and the module docs devote 40 lines to deriving why the brief was wrong (`heater.rs:50-90`). The brief's number would have been a *hardware defect*, not a fidelity gain.
- **The control law was deliberately *not* moved.** "Moving the *output* method must not move the control law, or every tuning in `defaults.h` would be wrong." The 1000 ms window and the 1 Hz sample survive untouched (`heater.rs:36-40`).
- **The heater gate is a whole new mechanism, from the recovered firmware, not from the C++.** A latching `HeaterGate` (held closed until the supervisor's first heartbeat, then a deadman) stands in front of the duty. `HeaterGate::new()` is the *only* constructor and there is no `new_armed()`, "so 'the gate starts open' is not expressible" (`heater.rs:526-548`).
- **`AtomicChopper` exists because the ISR cannot hold a `&mut IsrChopper`** (not `FnMut + Send`), and `unsafe_code` is denied, so no `static mut` either. Three atomics, and the counter is read/written **relaxed** because the ISR is its only writer; the duty is `SeqCst` because a half-published duty would be a window of the wrong power (`heater.rs:1690-1780`).
- **The ISR arithmetic was rewritten in integers.** `chopper_tick_level_ms` spells the comparison `>` where the `f32` reference must spell `!(a <= b)` — "That is not a drift, it is the one place the two *must* differ" — and the equivalence is proven over 1001 × 100 pairs (`heater.rs:257-271`, `:1992-2033`).
- **`duty_counts` rounds half-away-from-zero, not truncates.** Truncation "biases every duty *down* by half a count, which on a heater is a systematic under-power rather than a symmetric error" (`heater.rs:322-327`).
- **The ABP2 delay became a *deadline*, not a sleep.** "The ABP2 is a command-then-read device, so the 10 ms is a *deadline to wait until*, not a *duration to sit through*." `poll` writes on one tick and reads on a later one; the loop does 0 ms of pressure blocking (`abp2.rs:32-40`).
- **Two new error checks on the ABP2 that the C++ does not have**: `Wire.write`/`endTransmission` status is now read, and `requestFrom`'s return value is now checked. Both are deliberate divergences because the C++ converts *stale bytes* as if fresh (`abp2.rs:42-53`; tests `div1_a_short_read_is_an_error_not_a_stale_sample` `:790`, `div2_a_nack_on_the_command_is_an_error` `:810`).
- **S4 now gates the water *valve*, not just the pump** — a divergence, because the C++ checks `waterTankEmpty_` in `enablePump`/`setPumpPressure` only, and emptying the tank then entering a brew opened the valve against a dry reservoir (`cc-safety/src/lib.rs:33-38`).
- **S4 was made level-triggered.** The C++ kills a running pump *inside* `setWaterTankEmpty(true)` — an event on the empty→empty edge — so a missed edge leaves a pump running. The verdict is a level: "two consecutive empty readings behave exactly like one" (`cc-safety/src/lib.rs:44-50`; test `s4_the_tank_reading_needs_no_edge_to_take_effect`).
- **S5' is entirely new.** The C++ has *no* steam-valve whitelist, only `emergencyMode_`. Because steam and water share **one relay on GPIO17**, an ungated `openSteamValve()` "energises the very relay that S5 spends its whole existence keeping closed" — the C++ is protected only by the accident that nothing calls it. The port can express it, so it had to gate it (`cc-safety/src/lib.rs:432-540`).
- **The TSIC change-rate is applied in degrees, not counts**, against the C++'s raw-count reading — recorded as an unresolved ambiguity, with `COUNT_SCALE` exposed so the alternative is one multiplication away (`tsic306/mod.rs:110-136`).
- **The TSIC's 5 °C latch became per-instance**, reversing a `static` that made latching once-forever and process-global (`tsic306/mod.rs:93-99`).
- **The DS18B20 now applies a range check it never applied** (`isValidTemperature` was dead code) — which converts a genuine 155 °C over-temperature from a *hot reading* into a *sensor read failure*, so the machine reaches `SENSOR_ERROR` rather than `EMERGENCY_STOP`. The heater is off either way; the operator's message changes (`ds18b20.rs:66-84`).
- **The `MAX_BAD_READINGS` constant lives with the DS18B20 and is referenced by the TSIC**, because `max_bad_readings_` is a member of the shared `TempSensor` base — "so it is the same ten for both drivers" (`tsic306/mod.rs:550-560`).
- **The DS18B20 pipeline enforces the conversion time explicitly** rather than relying on the caller's 400 ms cadence, so a faster poller gets `Poll::Waiting` instead of a stale reading — an intentional difference from the C++ (`ds18b20.rs:30-33`).
- **Both pump watchdogs are now armed**, on the *activating edge* (where the pump is commanded on) rather than the state, and a trip emits a new `Effect::PumpTimeoutFired` so it is *visible in the field log*. The C++'s constants and its two actions are unchanged (`handlers.rs:464-500`; `effect.rs:160-180`).
- **The brew watchdog deliberately does not arm during `BREW_PREINFUSION_PAUSE`.** That state's `update()` pushes `DisablePump`, so a pause is not pump run time — "It is also a state the watchdog's own `isBrewActive()` guard accepts, which is exactly why arming on the state alone would have counted the pause against the five minutes" (`handlers.rs:494-500`).
- **`standby.started_at` became an `Option`.** The C++'s `standbyModeStartTimeMillis_ != 0` test is false at `millis() == 0` — "and every millisecond in a test harness — so standby can never fire". "This is the one place the port does *not* preserve a C++ artefact, and it can only make standby work *earlier*, never later" (`machine.rs:428-436`).
- **The temperature-sensor default was reversed back to `TSIC_306`.** An earlier revision defaulted to `DALLAS_DS18B20` *and* refused `TSIC_306`, on the sound-while-the-driver-was-missing reasoning that "a default the validator rejects could never be the machine's own configuration". The driver now exists, so the C++'s value is restored — and `ConfigViolation::UnsupportedTemperatureSensor` was deleted. "The four tests that used to assert a `TSIC_306` refusal are replaced, not deleted: the behaviour they pinned was real and worth pinning" (`cc-safety/src/lib.rs:112-118`; `cc-safety/tests/safety_paths.rs:840-895`).
- **`SetHeaterDuty` is now gated on the heater permission**, where the C++ emits the value and zeroes it microseconds later. "This port never asks the heater to be on when it must not be, even for the microseconds between the two C++ statements" (`cc-machine/src/lib.rs:466-483`).
- **The default hostname was changed from `silvia` to `test-cc-rust`**, decided 2026-09-29, because "the C++ and the Rust firmware are on the same network during the migration and would otherwise collide on `silvia.local`" (`cc-config/src/schema.rs:71-80`).
- **A C++-written NVS is ignored, not migrated** — decided 2026-09-28. The three things that make it safe are spelled out, including "a first boot with a C++-written NVS is indistinguishable from a first boot on a blank device, which is exactly the state the C++ firmware reaches on a factory reset anyway" (`cc-config/src/blob_store.rs:38-60`).
- **A bad value now rejects the whole import**, where the C++ logs a warning, continues, and reports success (`cc-config/src/lib.rs:41-45`).
- **The steam standby edge branch is preserved, and the code says it looks like a bug.** "Waking a sleeping machine with the steam switch already on does **not** steam. The operator has to toggle it off and on again. Preserved." (`cc-machine/src/handlers.rs:190-205`).
- **The MQTT plan was restructured from `std::map` iterators to three `usize` indices**, because iterators "are invalidated by any insertion" and there was "no way to ask 'how far through phase 1 am I?'" (`cc-domain/src/mqtt.rs:20-38`).
- **The retry backoff multiplier became an exact `num/den` rational** instead of `std::pow` in `double`, "so the schedule is a property of the code and not of the FPU" (`cc-domain/src/resilience.rs:28-34`).

## 5. Open questions and unverified claims left in the code

- 🔴 **The heater contactor is unmeasured, and the repository refuses to guess.** Three named gaps: (a) the contactor's minimum on-time/off-time — the software can only establish that the narrowest pulse is the C++'s own 10 ms, "whether 10 ms is *itself* long enough is a datasheet question"; (b) "Whether a hardware-PWM output is acceptable to the coil at all" — a contactor coil is inductive, and whether the rise/fall and any freewheeling path tolerate a 1 Hz square wave is "exactly as unknown as it was for the C++'s 10 ms one, but the *frequency* is now a new variable"; (c) "The realised frequency and duty on the pin… `ledc_timer_config`'s divider selection and the duty register have not been read back from hardware." **"Until a person with a scope, a dummy load and the boiler disconnected measures it, R1-07 stays open."** (`heater.rs:94-116`)
- 🔴 **The TSIC-306 driver has never run against a TSIC-306.** "A green test run here is not evidence that a TSIC-306 works." Named unknowns: clock tolerance, 31.25 µs pulses through a pull-up and a cable, behaviour on brownout, and "the one thing that actually matters for a heater — what it does when the supply dips" (`tsic306/mod.rs:5-21`).
- 🔴 **The TSIC device path (`GpioZacwire`) has never executed** and is not even in the firmware build, because the pin is carrying DS18B20 traffic. "Neither is evidence about the other" (`tsic306/mod.rs:22-30`).
- 🔴 **The change-rate units are an unresolved ambiguity, not a decision**: "This is an unresolved ambiguity, not a decision, and it is the single thing most likely to be wrong in this module" (`tsic306/mod.rs:110-124`).
- **The deadman timeout is invented, not recovered.** "Not recovered from the oracle — the binary's strings did not contain the value, only the phrase `deadman=armed`." 1000 ms is chosen from two constraints; "If R1-07's hardware test or a field report says otherwise, this is the constant to change" (`heater.rs:503-519`).
- **Doc 09 §4's recommendation is deliberately not implemented**: S1's debounce still lets the heater run ~800 ms above the emergency temperature. "Trip immediately on a reading above the threshold, use the debounce only for recovery" is recorded as a possible R4-09 divergence (`parity_findings.rs:222-226`).
- **`MANUAL_FLUSH_RUNNING` and the two `BACKFLUSH_*` phases run the pump and neither C++ timer covers them, so neither does the port.** "Extending a watchdog is a specification change, not a parity fix; it is recorded as a follow-up rather than smuggled in here" (`handlers.rs:517-521`).
- **`DISPLAY_OFF_NOT_PORTED` is a documented gap**, not a decision: `standbyModeRemainingTimeDisplayOffMillis_` is not ported (`machine.rs:420-436`).
- **Four C++ request setters don't reset the standby timer, and the C++'s own comment in `SystemStates.cpp:50-51` claims the hot-water switch wakes the machine.** It does not, because `hasUserActivity()`/`shouldExitStandby()` are `// TODO: Implement proper user activity detection` stubs returning false. Preserved and pinned; the fix would be a specification change (`states.rs:941-955`; `parity_findings.rs:668-686`).
- **The two "dead" 145 °C constants are preserved as dead**, not removed — a reader who greps `145.0` finds code that looks live and is not (`cc-safety/src/lib.rs:125-130`).
- **The C++'s eight `*_MAX_LENGTH` string constants are reproduced but not enforced**, because enforcing them "would reject configurations the C++ accepts" — so this firmware will still store a 4 KB hostname (`cc-config/src/schema.rs:28-40`).
- **`steam.setpoint` and `safety.emergency_temp` both claim order 203 in the C++**, preserved for `/api/parameters` ordering parity (`cc-config/src/schema.rs:29-31`).
- **The C++'s "Filter" on the ABP2 path and several other C++ quirks are reproduced rather than fixed** on the grounds that "removing a filter that changes every weight on a reversed cell is not a change to make while bringing a driver up for the first time" (`hx711.rs:50-62`).
