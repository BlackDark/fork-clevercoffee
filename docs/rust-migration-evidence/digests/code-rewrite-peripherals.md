## 4. Decisions reversed or corrected during implementation

- **LEDC → 10 ms GPTimer ISR for the heater.** The design's own "1 Hz carrier, hardware duty, strictly better than an ISR" argument was correct as far as it went and *incomplete*: it never checked `ledc_ll_set_duty_start`. Recorded as a self-correction, not a defeat (`crates/cc-firmware/src/main.rs:216-222`).
- **`LedcPwm` is kept, unbrought-up**, behind the same `HeaterDuty` seam, because the spin is unique to the original ESP32 and is the transport a different target wants (`heater.rs:187-197`, `311-313`).
- **The `ledc` peripheral is *not taken at all*.** `let _ = peripherals.ledc;` — "taking the peripheral is how the previous build ended up one step away from calling `ledc_set_duty_and_update`" (`crates/cc-firmware/src/main.rs:441-449`).
- **Heartbeat synthesised from the tick count → read from the real clock.** It was `tick * HEARTBEAT_MS`, "a *guess* at the clock… only the elapsed time if every tick took exactly `CONTROL_TICK_MS`". The 1000 ms period was *exactly* `DEADMAN_TIMEOUT_MS`, leaving no margin; 400 ms is "comfortably inside it" (`main.rs:96-111`).
- **R1-01's three justfile recipes marked DEVIATION D1/D2/D3**: host recipes must pass `--target` explicitly (`.cargo/config.toml` sets `[build] target` for *every* cargo invocation, so `cargo test` would try to build `std` for Xtensa); device recipes must source `.rust-esp-env.sh` for `xtensa-esp32-elf-gcc`; `flash` must pass the partition table because "the first byte of the app is the 0xE9 app magic, and the table is a separate image at 0x8000 — so the table must be flashed or the bootloader cannot find app0" (`justfile:5-21`).
- **`ESP_IDF_SYS_ROOT_CRATE := "cc-firmware"`** added after R1-01 found that `esp-idf-sys` reads `[[package.metadata.esp-idf-sys]]` *only from the root crate*; without it the metadata is **silently ignored** and `svc::fs::littlefs` later fails with a confusing error (`justfile:38-48`).
- **`RUSTUP_TOOLCHAIN := "esp"`** exported globally because an ambient `RUSTUP_TOOLCHAIN=stable` makes every device recipe fail with "the -Z flag is only accepted on the nightly channel" *and* makes host recipes silently run on the wrong compiler (`justfile:50-58`).
- **A global `export PATH := … + ~/.cargo/bin`** because "a just `export` assignment is injected into EVERY recipe's environment" — R1-01 left half the recipes failing with "command not found" (`justfile:29-36`).
- **`mon-headless` stopped expanding `$VIRTUAL_ENV`** under `set -u` ("VIRTUAL_ENV: unbound variable" on every shell an agent runs); it now probes `.embuild/espressif/python_env/*/bin/python` for pyserial (`justfile:355-374`).
- **`the_console_drain` was moved out of `cc-firmware` into `cc-hal-esp32::restart`** because `cc-firmware` is a `[[bin]]` with `harness = false` and "a binary's unit tests are not built for a target it cannot run on" (`restart.rs:20-27`).
- **The scale bring-up override shipped as `false`**, reversing the "ON in this build" default, after the 2026-09-29 measurement showed the sampling task is not what costs the tick — "leaving it on would mean a shipped firmware ignores a setting the operator controls, which is the shape of 09 §23" (`main.rs:274-283`).
- **The probe is selected from the board, not the config** (`const PROBE = DallasDs18b20`), with the config's value logged alongside; the C++ default is preserved where the C++ keeps it and the board's actual probe is not overridden by it (`main.rs:125-152`).
- **`Tank` reading: `fitted && raw` → `if fitted { raw } else { true }`.** The rule generalised in the comment: "never gate a 'assume the safe value' fallback behind the presence of the thing it stands in for" (`crates/cc-hal-esp32/src/switches.rs:355-380`).
- **PID mode cache seeded from `runtime_pid` → seeded from `Controller::in_automatic()`.** Found on hardware: the first tick saw `permitted == pid_mode_enabled`, never called `set_mode(Automatic)`, and `compute()` returned `false` every tick — the machine sat in `PidNormal` with a live setpoint, a 7 K error and a **permanently zero heater duty**, logging `P=0.0 I=0.0 D=0.0` (`crates/cc-firmware/src/control.rs:157-176`).
- **`setpoint` and control config are a clone owned by the control task**; `POST /api/parameters` is visible to the state machine on the next event but to `/api/config` only after a reboot. "That asymmetry is real and is recorded, not papered over" (`main.rs:798-815`).
- **The radio moved into the control task** — before this, "the radio was polled nowhere and `/api/status` reported `wifiAssociated: false` on a machine that was associated" (`main.rs:832-838`).
- **The network stack is initialised unconditionally**, not inside the Wi-Fi branch (see §2 #9).
- **`log_muted()` is a correct flag with no consumer yet** — a stated gap: "the moment R3-11's telnet pump lands … a flag that is wrong on arrival would not be noticed until a credential leaked" (`provisioning.rs:174-192`).
- **SSE is the C++'s shape, not a hand-rolled stream** — handler returns, broadcaster task writes; and the C++'s `AsyncEventSource` model is named as the reason the C++ has no such failure (`web.rs:56-70`).
- **Display init sequence taken from the C++/U8g2, not from the `ssd1306` crate's `DisplayConfig::init`** — a deliberate deviation from the crate's defaults, because three of its init commands disagree (`display.rs:38-56`).
- **The `Display` is heap-allocated once**, not a stack local in `refresh_display` (see §2 #13).
- **Scale commands became the first non-inert web commands.** In the C++ they set a flag on a `SensorCoordinator` that has no scale registered: "accepted, answered 200, and with no effect on any hardware" (`main.rs:1762-1770`).
- **`STEAM` toggle maps to two reducer requests.** `POST /api/steam` *toggles* in the C++; the web layer here sends the intended value, so it becomes `SteamStart`/`SteamStop` (`main.rs:1848-1860`).
- **The scenario-format document is subordinate to the parser** — stated as policy at `crates/cc-parity/src/scenario.rs:4-7`.

## 5. Open questions and unverified claims left in the code

- **The heater has never been energised by this code and must not be until R1-07's safe test procedure has been run with the boiler disconnected.** What *is* verified is the arithmetic and that the firmware "boots with the timer running and the gate closed". R1-07 stays open (`heater.rs:198-215`; `main.rs:50-57`; `intentional-diffs.md` #5).
- **The contactor's minimum on/off time is unmeasured.** The software guarantees it never asks for a pulse narrower than 10 ms; "whether 10 ms is *itself* long enough is a measurement" (`heater.rs:205-210`).
- **The realised duty on the pin is unmeasured.** "100 entries a second that are *supposed* to be 50 on and 50 off could be 51 and 49 and no host test would know" (`heater.rs:211-215`).
- **`measured_on_fraction()` is a measurement of the ISR's counters, not of the pin** — "nothing has been scoped" (`heater.rs:614-624`).
- **Nothing is known about the relay board's actual trigger polarity in the field (R0-01).** If the board were wired `LOW_TRIGGER`, `Level::Low` would energise the heater, pump and valve on *every* boot; the oracle refused `LOW_TRIGGER` heater configurations outright and R2-06/R3-03 must reproduce that refusal (`main.rs:36-48`).
- **Whether `FreeRtos::delay_ms` is systematically short, or the measured 12 ms was the tick grid landing unluckily** — explicitly an open question, deliberately not asserted; owned by R2-09b (`time.rs:144-147`).
- **The ZACwire/TSIC-306 path has no hardware evidence at all.** No TSIC-306 is fitted; the capture is not even brought up in the firmware build. "Every claim below is either read out of the installed sources or host-tested against a synthesised waveform. **None of it is evidence that a TSIC-306 works.**" (`zacwire.rs:5-13`; `main.rs:271-275`).
- **`log_muted()` has no consumer.** The 30 s window is the *only* thing enforcing provisioning rule 5 on this build; adding a reader is "one `if`" away and is a stated gap, not an oversight (`provisioning.rs:174-192`).
- **The `ZACwire` driver's flash cost is unmeasured** because the TSIC branch is dead-code-eliminated on the DS18B20 image; "that is stated rather than glossed: `just size` measures the `DS18B20` image" (`main.rs:149-152`).
- **The MQTT client has never connected to a broker.** `mqtt.enabled` defaults to `false` and the broker is empty, so no client is constructed on this machine. "A session against a real broker is a deployment question" (`mqtt.rs:35-44`).
- **SH1106 support is a dropped *option*, not a verified equivalence** — recorded in `intentional-diffs.md` and deliberately not exercised (`display.rs:31-40`).
- **The scale has no load cell, amplifier or wiring on GPIO32/25/33** on this machine, so the driver will report the weight absent and raise its fault within `SIGNAL_TIMEOUT` (100 ms). "That is the honest outcome and the boot log says so" (`main.rs:262-268`).
- **An unsafe NVS blob is kept rather than erased, on purpose** — the diagnosis has to survive a reboot, but the cost is that every subsequent boot re-reports `DiscardedUnsafe` (`network.rs:29-34`).
- **The heap is OOM-shaped near the boundary**: `/api/parameters` and `/api/config` answer `503` below 30 KB rather than risking "an OOM [that] is a reboot in the middle of a shot" (`web.rs:119-127`).
- **A poisoned I²C bus is reported, not unwrapped** — "a poisoned bus means the pressure sensor and the display have both already lost, and a second panic during bring-up recovery would hide the first" (`display_shared.rs:60-68`).
- **The `#[allow(unsafe_code)]` blocks need a human to ratify them** — two in the workspace (`esp_timer_get_time` and the three `httpd_*` calls), each with its reasoning at the call site (`lib.rs:4-46`; `time.rs:34-44`; `heap.rs:44-52`).
- **`size-bench` is a placeholder** until R2-09b (`justfile:404-405`).
- **The `cc-device-tests` runner degrades to "start at zero every boot" if NVS cannot be opened**, "which turns a failing case into a loop rather than a progress" (`cc-device-tests/src/main.rs:434-441`).
