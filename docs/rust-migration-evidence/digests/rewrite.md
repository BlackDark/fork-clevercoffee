## 1. Target architecture (as this branch proposes it)

- **Platform:** `esp-idf-svc` `=0.53.0` / `esp-idf-hal` `=0.47.0` / `esp-idf-sys` `=0.38.1`, ESP-IDF `v5.5.5`, target `xtensa-esp32-espidf`, `std` enabled, built with `-Zbuild-std=std,panic_abort` and `RUSTFLAGS="--cfg espidf_time64"` (04; 02 §7.1; 05 §4).
- **Workspace at the repository root** (not a subdirectory), with a *separate* `rust/partitions_4M.csv` because the root `partitions_4M.csv` stays C++-owned until R4-10 (04 §6).
- **Crates:** `cc-domain` (units, 18-variant `MachineState`, `Pid`, `EmergencyPolicy`, `WaterFlowPolicy`, `InterlockPolicy`, `Shot`), `cc-safety` (`no_std`, zero-IO pure reducer → `SafetyVerdict`), `cc-config` (96→98-key `ConfigSchema`, `trait ConfigStore`, serde_json import/export, `Secret<T>`), `cc-machine` (18-state machine, handlers, `Reducer`, `Event`/`Effect`, `trait Hardware`/`Clock`/`TelemetrySource`, sensors + rate-of-change filter), `cc-display` (`[u8;1024]` framebuffer, `no_std` no-alloc, U8g2-compatible draw calls, 6 templates), `cc-hal-esp32` (**the only crate importing `esp-idf-*`**), `cc-provisioning` (SoftAp/DnsIntercept/PortalHttp), `cc-firmware` (one binary named `firmware`, board selected by `board-*` feature), plus `cc-parity` (harness, 04 does not list it but 10/notes do) — 10 crates total (notes).
- **Concurrency model:** FreeRTOS tasks, *three* boundaries only — `control` (prio 5, core 1, 8 KB stack, 100 Hz), `provisioning` (prio 4, spawn-once-only), `housekeeping` (prio 2, core 0) — plus lwIP/httpd at 3. The `spawn_*` functions are the *only* place that knows about threads, so the executor is swappable (04 §2–3).
- **State machine location:** in `cc-machine` as an Elm-style reducer — `reduce(&Machine, &Context, Event) -> (Machine, Vec<Effect>)`; the tick is SENSE → DECIDE → ACT → NOTIFY, and `applier::apply()` is the sole caller of `Actuators`/`HeaterOutput` (04 §3.1).
- **Queues:** `hal::task::queue::Queue<Command,32>` (drop-newest in) and `Queue<Event,32>` (drop-oldest out), both requiring `T: Copy` — no `String`/`Vec`/`Box` in a cross-task message. Sensor→Event and Event→Effect→actuator are **direct same-tick calls**, deliberately not queued (04 §3.2).
- **Hardware abstraction:** one `Board` trait + one `Esp32DevkitC` impl + a `PinMap` const with a build-time `assert_valid()` (the chip-aware replacement for `pinmapping.h`'s 21 `static_assert`s); one crate rather than seven so the pin map is edited in one place (04 §6).
- **Single-ownership table:** heater pin → `HeaterOutput`; pump + valve → `Actuators` with the C++ `ValveState` enum preserved verbatim (one relay multiplexed steam/water); I2C → `I2cBus` mutex; NVS → `NvsStore`; watchdog → moved into the control task (04 §7).
- **Watchdog:** `TWDTDriver` 5 s, `panic_on_trigger = true`, **moved into** the control task which calls `watch_current_task()` itself; `TWDTConfig::subscribed_idle_tasks` set explicitly so idle tasks do not feed (04 §3.4 correction).
- **Config persistence:** a single nested JSON blob in NVS under a `cc.`-prefixed namespace — **no C++ backward compatibility**; the C++'s dotted key *names* are kept for familiarity, the C++'s FNV-1a hashed-key scheme is not (08 §5.3/§6; 07 §2; 06 R3-08).
- **Startup:** outputs to inactive level *before* drivers are configured, post-init readback assertion, watchdog up but not fed, display before config, then an **actuate-the-emergency-stop check** (trip, verify heater command is zero, clear) that the C++ does not perform (04 §4).
- **Shutdown:** three named levels — `safe_hardware_shutdown` (not latched), `emergency_shutdown` (latched), `boot_halt` (init failure before a display exists: relays off, loop forever, never `exit(0)` as `main.cpp:122-126` does) (04 §4).
- **Safety as the type system:** `water_flow_allowed(state)` and `steam_flow_allowed(state)` are `match`es with **no wildcard arm**, so a 19th state is a compile error; the emergency latch is a precondition *inside* `Actuators::enable_pump/enable_heater/open_*` rather than a call-site discipline; `heater_enabled` boolean deleted entirely (04 §5; intentional-diffs §2).
- **Heater path:** `HeaterOutput` behind a `HeaterDuty` seam with `LedcPwm` (retained, unbrought-up) and `AtomicChopper`/`IsrChopper` in `cc_domain::heater`; window arithmetic host-testable, pin in `cc-hal-esp32` (04 §5; 09 §17/§20).
- **CI-enforced crate hygiene:** a `cargo tree` grep proving `cc-domain/safety/machine/display/config` do not depend on `esp-idf-{svc,hal,sys}`, plus greps forbidding crate-root `#![allow(…)]` (04 §6; 05 §6).

## 2. Key decisions and their rationale

| Decision | Chosen | Why | Rejected alternatives |
| --- | --- | --- | --- |
| Platform stack | `esp-idf-svc` 0.53.0 on ESP-IDF v5.5.5 with `std` | Only option covering HTTP, OTA, NVS, filesystem, TCP/IP; vendor Wi-Fi/lwIP/mbedTLS drivers (03 Context, Option A) | `esp-hal`+`esp-rtos`+`esp-radio`+embassy (bare metal) — no HTTP/OTA/NVS/FS, unverified TCP/IP, no task WDT; hybrid dual-HAL; Arduino+FFI |
| Concurrency runtime | FreeRTOS tasks + one async-capable control task | `embassy-executor` is not ISR-safe on esp-idf-svc (its `critical-section` is a FreeRTOS recursive mutex); `edge-executor` 0.5.0's ISR safety is unassessed; FreeRTOS gives explicit priorities and per-task watchdog subscription (03) | embassy, edge-executor 0.5.0 |
| Task count | Exactly three; everything else cooperative in the control task | Only three activities need independent contexts: control deadline, heater timing, unbounded HTTP work (04 §2) | Per-subsystem tasks, event broker/actors inside control task |
| Priority relationship | Control task prio 5, above lwIP's 3 | Turns ADR-0002's accidental priority-10-network-preempts-priority-1-control inversion into a designed, testable property (04 §2) | Inheriting the C++'s priority assignment |
| Heater output | 10 ms GPTimer ISR (parity), `LedcPwm` retained unbrought-up behind `HeaterDuty` | The contactor-friendly 1 Hz LEDC carrier panics the original ESP32 (INT WDT, 300 ms) through `ledc_ll_set_duty_start`'s spin inside `portENTER_CRITICAL` (09 §17/§20; intentional-diffs §9) | LEDC at 1 Hz/`Bits17` (R1-07's original decision, reversed); LEDC at ≥3 Hz (reintroduces 6 contactor ops/s) |
| NVS compatibility | None; Rust owns `cc.`-prefixed keys, keeps C++ dotted *names* | Frees the design from replicating FNV-1a hashing; oracle showed the dotted names are a good schema (07 §2; 08 §6) | Reading C++-written NVS |
| Config storage shape | One serialised JSON blob (~2.1 KB) in NVS | Atomic, versionable, simpler than 96 hashed scalar keys; oracle's 2,071 B vs the port's 2,077 B is corroboration (08 §5.3; 09 corroboration) | Per-parameter hashed NVS keys (the C++ scheme) |
| OTA story | Forced full flash over USB is primary; HTTP OTA optional and *first* to drop; `espota` desirable | Decided 2026-09-28, "do not re-litigate"; HTTP OTA is the single largest optional feature (07 §2, §3) | Making HTTP OTA a requirement |
| UI | React SPA in `ui/` unchanged, embedded via `include_bytes!`; only the live-event transport negotiable (SSE vs WebSocket) | Removes `buildfs` and a class of "UI didn't update" bugs; allows `spiffs` to shrink to ~64 KB (07 §2) | Keeping the SPA in LittleFS only; rewriting the UI |
| Partition rebalance | Maximise `min(app0,app1)` with `nvs`/`otadata`/`coredump` byte-identical; target 1,835,008 B slots, 393,216 B FS (oracle's table) | 154 KiB of C++ headroom cannot hold a Rust esp-idf image; formula = `(4,063,232 − S)/2` (07 §1) | "≥ 2 MB per slot" — arithmetically impossible by 131,072 B; leaving the C++ table alone |
| Safety invariants | 11 paths S1–S11 must be *fixed* not replicated where they are C++ bugs; the emergency latch moves inside the actuator methods; whitelists are compile-time exhaustive | 5 of 11 C++ safety paths were defective (dead pump timeouts, no steam whitelist, ungated water valve, missing config registration, OTA actuator gap) (01 §6; 09) | Faithful bug-for-bug parity (explicitly rejected as "silently deleting a check whose comment says 5-minute max brew time") |
| Config fail-closed policy | Cross-parameter validation, refuse `LOW_TRIGGER` heater relay, discard an unsafe stored config and run defaults, refuse to store an unsafe one | Adopted from the recovered oracle; a 5 s watchdog reset is a long time to leave a heater energised (08 §4.1, §6) | Storing whatever validates per-parameter (the C++ behaviour) |
| Scale features | **Keep** HX711 (R3-17) and Acaia BLE (R3-18), make them actually work | Human owner declared the C++ deadness their bug, not a drop decision; the original ESP32 *does* have BLE (01 §3 superseded; intentional-diffs §11) | The plan's own earlier recommendation to drop F13/F14 |
| Default hostname | `test-cc-rust` (not `silvia`) | Both firmwares share a network and diverge deliberately; the name must say which answered. `mqtt.password`'s `"silvia"` is left alone — it is a credential (intentional-diffs §12) | Brand-neutral name; renaming the credential too |
| SH1106 | Undecided; default is "drop and document" | `ssd1306` has no SH1106 and `sh1106` 0.5.0 is stuck on `embedded-hal 0.2` (06 open decisions) | Porting a fork |
| Display draw target | Own framebuffer + U8g2-compatible calls, **not** `embedded-graphics::DrawTarget` | `no_std` no-alloc + bit-exact U8g2 parity (RLE fonts 42,722 B vs `ImageRaw` 177,723 B, a 135,001 B saving) — but recorded as **open, not decided** (intentional-diffs §6) | A thin `DrawTarget` adapter, or routing drawing through the trait |
| Coredump | Partition reserved, `CONFIG_ESP_COREDUMP_ENABLE_TO_NONE=y` left alone | Enabling it is a one-line change but it changes crash-time behaviour of the shipped image and costs flash — a gate decision (07 §10.2) | Flipping it in as a side effect of a size reduction |
| Validation command style | `just` recipes, positional args only, explicit `PORT` with no default | `KEY=value` is make syntax and would pass the literal `MCU=esp32` to `espflash` at the moment an agent touches hardware (05 §3–4; checklists §B) | `make`-style recipes, port globbing |

## 3. Pitfalls, gotchas and hard problems discovered

1. **🔴 Both pump safety timeouts are dead code in the C++.** `PumpTimer::isExpired()` returns false unless `isRunning_`, which is only set by `PumpTimer::start()` — and `start()` has **zero call sites** in the tree (six references: two members, two ctor args, two reads). The 5-minute brew and 60-second hot-water limits can never fire; hold the water switch and the pump runs indefinitely on a machine with a 2 kW boiler. *Severity: blocker (C++), closed in Rust on the pump-on edge with a verbatim `logError` message.* (09 §11; intentional-diffs §1)
2. **🔴 The steam valve has no safety whitelist at all, and steam and water share one relay.** `openSteamValve()` checks only `emergencyMode_`; there is no `steamSafetyShutdownCheck` anywhere. `ValveState.h:8-11` states steam and water share the same physical relay, and the pin map agrees (GPIO17) — so an ungated steam valve *is* an ungated water valve. Closed in C++ only by the accident that `rg -n openSteamValve` finds no call site. *Severity: blocker.* (09 §2; intentional-diffs §2; notes R1-07)
3. **🔴 LEDC cannot do a contactor-friendly carrier on the original ESP32 — it panics at boot.** `ledc_ll_set_duty_start` (esp32's `hal/ledc_ll.h:485-489` only) spins on `conf1.duty_start` inside `portENTER_CRITICAL(&ledc_spinlock)` with interrupts masked, up to one full carrier period. At 1 Hz that is ~1 s against a **300 ms** interrupt watchdog — and it panics at duty 0 too, so `just flash` was landing images that died before the control task. *Severity: blocker; R1-07 reversed, 10 ms GPTimer ISR restored.* (09 §17/§20; intentional-diffs §9)
4. **🔴 An FPU instruction in a level-1 ISR panics the original ESP32, and the Rust source hides it.** Xtensa does not save coprocessor state in an interrupt; `CONFIG_FREERTOS_FPU_IN_ISR` defaults `n`. GCC soft-floats the C++ comparison, but LLVM (the `esp` toolchain, `target_feature="fp"`) emits real `ufloat.s`/`ult.s`. `AtomicChopper::tick`'s `self.duty_ms() as f32` was redundant and fatal. There is **no compile-time warning** — the check is `objdump` + a careful FP-instruction grep (a naive `.s` grep also matches `divn.s`, `un.s`, `moveqz.s`). *Severity: blocker for every ISR this firmware will ever write.* (09 §22)
5. **🔴 The C++ ISR rate is not its switching rate — a 100 Hz carrier would switch the contactor 200×/s.** The 10 ms ISR predicate `pidOutput > counter` is monotone, so the relay level changes twice a second and not at all at duty 0 or full duty. An earlier revision of 04 §5, `intentional-diffs` #5 and both crate module docs specified 100 Hz "because it reproduces the 10 ms-step / 1 Hz chopping exactly" — self-corrected in place, including the discarded resolution table (valid bits at 100 Hz are 10–19, not 8–10). *Severity: major (mechanical safety of a 2 kW contactor).* (04 §5; notes R1-07; intentional-diffs §5)
6. **🔴 S1 keeps the heater energised through its own debounce window.** Emergency stop needs three consecutive readings above threshold at a 400 ms sensor cadence, so the heater stays on for up to ~800 ms while already above the emergency temperature. Preserved on purpose, flagged "real exposure", needs a human decision. *Severity: major.* (09 §4; intentional-diffs preserved table)
7. **🔴 The entire scale stack is structurally absent while the API pretends it exists.** Nothing calls `HardwareContext::setScale()`, so `scale_` is always null, `getScale()` always null, `DisplayWidgets.h:324`'s null check is always false, no weight is ever produced, and MQTT/web tare + calibration commands "return success and have no effect". `main.cpp:145-150`'s log line claims support is present. Ported anyway (human's decision), so R3-17/18 have **no C++ parity baseline by construction**. *Severity: major.* (09 §23; intentional-diffs §11)
8. **🔴 The Rust control tick already overruns its own 10 ms budget in ~62 % of ticks** (86 of 138, worst 3.2×) and it is **not** the scale — a build with sampling disabled is *more* frequent (111/136). R4-01b's "zero ticks > 10 ms" acceptance currently fails and the fix must not be relaxing `TICK_BUDGET_MS`. *Severity: major.* (09 §24; notes)
9. **A timing instrument that has never disagreed with a result is not known to be working.** The first tick-cost instrument took its timestamp *after* `delay_ms(CONTROL_TICK_MS)` and reported ~431 ms for a 400 ms period — it would have hidden the real overrun. The HX711's "tick unaffected" criterion passed *because* of this. *Severity: major (process lesson).* (09 §24)
10. **🔴 The S1 debounce is only meaningful at the sensor cadence.** Running the safety monitor on the 10 ms control loop made S1's three-reading debounce trip on a single reading repeated 30× in 300 ms, making the most safety-relevant timing constant in the firmware untestable. The monitor must run at 400 ms. *Severity: major.* (10/notes R1-08; 06 R1-08 status)
11. **ESP-IDF's `httpd` is one task, so a pull-style `/events` starves the whole HTTP server.** With one SSE client connected, 150 consecutive `/api/parameters?filter=all` requests all timed out, answering in 22–140 ms a second after the stream closed. The C++ does not have this: `AsyncEventSource` returns from the handler and pushes from the loop task. **R3-14 is explicitly declared "not at parity"** — `Sse::broadcast` exists and is not wired. *Severity: blocker for the UI.* (notes, R3 findings #3)
12. **`app_main`'s stack is 3.5 KB and the startup path needs ~11 KB**, surfacing not as a stack-overflow report but as `assert failed: block_trim_free … (block must be free)` — an allocator assert on corrupted DRAM. Fix: a 16 KB `bring-up` task. Lesson: size every task's stack from `.debug_frame`, not from a feeling; `CONTROL_STACK_BYTES` was a guess. *Severity: major.* (notes, R3 findings #1)
13. **A `u32` wrapping_sub in the provisioning password window made the window zero milliseconds.** `now.wrapping_sub(opened + WINDOW) >= WINDOW` is true on the first poll after `wifi set`, so every password line was parsed as a command and rejected — with a success-looking `ok ssid accepted` on the console. *Severity: major; also the flagship example of finding 15.* (notes, R3 findings #2)
14. **There was no `just test-esp32`, so ~50 `cc-hal-esp32` unit tests were type-checked and never executed** — which is the whole story of findings 13 and 15. Now 89 device tests run. *Severity: major (process).* (notes, R3 findings #5)
15. **`esp_restart()` does not flush UART0**, so the last two lines before a reboot are always lost; every reboot path needs a `uart_wait_tx_done`. *Severity: minor.* (notes, R3 findings #4)
16. **`esp-wifi-provisioning` is a landmine**: it forces `esp-idf-hal/rmt-legacy` **non-optionally**, and cargo feature unification turns it on for the whole graph — removing `hal::onewire` and the GPTimer module, which would break R3-06 and the heater fallback. The check must be step 0 of R1-06, not step 1. *Severity: blocker if adopted blindly.* (06 R1-06; README)
17. **Static RAM, not flash, is the binding constraint: 131,688 B = 41 % of the ESP32's 320 KB**, roughly double the pre-network figure, and ADR-0002's 30 KB heap-shed threshold was tuned against ~75 KB. 94,155 B of it is `.iram0.text` dominated by the prebuilt Wi-Fi MAC (`libpp.a`/`libnet80211.a`, `CONFIG_ESP_WIFI_IRAM_OPT=y`) and **no Rust-side change touches it**. *Severity: blocker for ADR-0002's margin.* (07 §12)
18. **`std` itself pulls in 210 KB of backtrace symbolisation** (`std::panicking::default_hook` → `backtrace_rs` → addr2line/gimli/object/miniz_oxide) — useless on a device with no symbol table. Removed with one line, `build-std-features = ["std/backtrace-trace-only"]`, for **−162,656 B flash (−12.05 %)**. The RAM win was only 1,440 B, not the 10 % implied. *Severity: major, and a template for a "measured rather than assumed" outcome.* (07 §9, §9.5)
19. **mbedTLS (~94 KB flash, ~8 KB RAM) is not removable and it is not our code.** `mqtt` → `tcp_transport` → `esp-tls` → mbedtls, with the MQTT client calling `esp_tls_get_and_clear_last_error()` unconditionally even for plain TCP; and `esp_wifi` → `wpa_supplicant` for WPA3/Enterprise. Cutting it is a *product* decision (which APs the machine can join), not a size optimisation. *Severity: major.* (07 §11)
20. **`CORE_POWER_OF_FIVE_128` is 10,416 B of `.dram0.data` (7.9 % of all static RAM)** — copied from flash at boot for one `f64::from_str` that the config schema genuinely needs. Removable only by making the schema integer-only or relocating the table. *Severity: minor-to-major.* (07 §12.3)
21. **`&TWDTDriver` does not compile across a thread boundary** — `Send` but **not** `Sync`, and `WatchdogSubscription` is `PhantomData<&'s mut ()>`. The workable design is the inverse: *move* the driver into the control task. Also, "only the control task subscribes" is not automatic — IDF subscribes idle tasks unless `CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0/1` are set to `n`. *Severity: major (compile + a silently wrong watchdog).* (04 §3.4; notes correction #6)
22. **`heapless::Deque` cannot be a cross-task channel** and `hal::task::queue::Queue<T>` requires `T: Copy` — an earlier draft specified a deque and then forbade locking, which is a contradiction. `Command`/`Event` must be `Copy`; no `String`, `Vec`, or `Box` in a message. *Severity: major (architecture).* (04 §3.2; notes correction #7)
23. **U8g2 quirks that only an oracle finds, and the obvious port gets each wrong**: `U8G2_BALANCED_STR_WIDTH_CALCULATION` is on by default (inset first glyph → 1–2 px narrow, moves every centred/right-aligned label); `u8g2_uint_t` wraps so an underflowed coordinate *intersects* and a glyph starting above the display is clipped, not dropped; `drawCircle`/`drawDisc` draw 8 pixels/lines per section, not 6/12; the degree sign is one Latin-1 **byte**, so a Rust `"\u{b0}"` measures 30 px instead of 25; and the bare vs `prepareDisplay`-prepared display differ (`ExtendedText` uses `ascent_para` 7 vs `ascent_A` 6, and without `pos top` the Modern template's `fub20` at y=14 renders at rows −9..13, clipped off the top). *Severity: major (pixel-level, and each found by the oracle, not by reading the C++).* (docs/display-parity.md)
24. **Config-schema landmine: `safety.emergency_temp` / `safety.emergency_hysteresis` are defined and read but never registered** in `getAllConfigParams()`, so they are never loaded, saved, exported or importable and **silently reset to the compiled default on every reboot** — a live over-temperature-settings bug on safety path S1. Fixed in Rust with a test that fails against the old behaviour. *Severity: blocker (C++), fixed.* (01 §10; notes findings #1)
25. **PID integer division by zero.** `PID_v1.cpp:85` divides by `SampleTime / 1000` with `unsigned long`, so any window < 1000 ms makes the divisor 0 and the output `NaN` — and the library's clamp `if (x>max) … else if (x<min)` lets `NaN` through. The shipped firmware escapes only by coincidence (`sample time == processWindowSize() == 1000`). Any heater-output change trips it. Scenarios A–C are bit-identical after the fix; scenario D is **retained in the oracle as the C++'s NaN on purpose**. *Severity: major.* (09 §1; intentional-diffs §4)
26. **The shipped PID gains make the controller behave like bang-bang control** (`kd = Tv·Kp = 713`, ~7130 ms⁻¹; a 3.1 °C change moves the D term by ~22,000 against a 1000-wide window; output alternates 1000 → 0 → 0). Preserved faithfully; flagged as worth someone's attention independent of the port. *Severity: minor (product).* (09 §7)
27. **The emergency threshold constants are dead.** `EMERGENCY_THRESHOLD_C = 145.0` and `EMERGENCY_RESET_THRESHOLD_C = 120.0` are read nowhere; the live default is `emergencyStopTemp` = 150.0 (range 120–180). The C++ test suite's "145" is a fixture. *Severity: minor, but a trap for parity.* (09 §5)
28. **The C++ config validator is per-parameter only**, so `steam.setpoint = 140` with `safety.emergency_temp = 120` is accepted — a machine that cannot be steamed. Rust adds the oracle's cross-parameter rule. *Severity: major.* (09 §8; intentional-diffs)
29. **`safety.emergency_temp > steam.setpoint + hysteresis`, refuse `LOW_TRIGGER` heater relays, and discard/refuse unsafe configs — the C++ honours `trigger_type`, so it permits a configuration that is unsafe on reset** (an undriven GPIO during reset energises a 2 kW heater). All three rules recovered verbatim from the flash dump and adopted as requirements. *Severity: major.* (08 §4.1)
30. **C++ behaviours deliberately preserved (accidental but load-bearing):** `SENSOR_ERROR`'s recovery clock is measured from *entry*, not from when the error clears, because the sensor-error guard has no exclusion list so `checkSpecificTransitions()` is never reached (`ErrorStates.cpp:49` is unreachable); all four backflush `update()`s only log, so `BackflushFillingState` never re-asserts its pump or valve and `BackflushFlushingState` never re-closes; `hasUserActivity()` is a hard `return false` so the water switch cannot wake standby; `powerOff()` shuts down *before* requesting standby so for one loop `PidNormalState::update` re-enables the pump; the anti-windup gate is a strict interior test with a 0.01 dead band; eight string-length constants are never enforced. *Severity: major (each pinned by an `s<N>_` test precisely so a future reader does not "fix" it).* (09 §12–§15; intentional-diffs preserved table)
31. **The DS18B20 layer has three real defects, one of which this branch corrected twice.** `rawToCelsius` folds every raw `≤ DEVICE_DISCONNECTED_RAW (−7040)` to −127, which is *exactly −55 °C in 1/128 units* — the bottom of the sensor's range is reported as disconnected. All six faults are in fact rejected, but all six are reported as "Temperature sensor not connected", so a probe power-on-reset sends an operator to look at the wiring. And `TempSensor::isValidTemperature` (−50..150 °C) is dead code, so a 165 °C reading is cached, averaged and handed to the PID on the Dallas path. §17 of 09 was written **wrong** and carries a bold retraction at the top; §18 is the correction, and a test named `div7_every_ds18b20_fault_is_rejected_by_the_cpp` exists specifically so the correction cannot be re-inverted. *Severity: major.* (09 §17–§18, §21; intentional-diffs §7–§8)
32. **TSIC-306 change-rate constant used in two different units in two adjacent C++ files**: `ZACwire.cpp:58` compares it against a gradient in **raw counts** while `TempSensorTSIC.cpp:39` compares it against **degrees**, with a `//grad is [°C/s]` comment in the counts code. Under the count reading the effective limits are ≈19.5 and ≈0.49 °C/sample. Flagged unresolved, not decided. Compounded by: the C++'s no-signal timeout is 100 ms against a 10 Hz sensor (one period, zero margin) and `validTemps` is a function-local `static` inside a `const` member function (process-global, never reset). *Severity: major, "the single most likely thing to be wrong in the module".* (09 §21; intentional-diffs §7)
33. **TSIC-306 is unverified on hardware and never has been.** The pure decoder is host-tested against a *synthesised* waveform (which proves the arithmetic and nothing about a real sensor); `cc_hal_esp32::zacwire` is implemented and **never brought up** because GPIO16 is carrying 1-Wire traffic; the `esp` target has no `AtomicU64` (edge ring packs level+31-bit timestamp into one `AtomicU32`) and no safe timestamped per-edge callback, so capture is a ≥128 kHz **poller**, not the falling-edge ISR the app note suggests. `temp >= 180 °C` can never fire (span ends at 150) and `temp <= 0.0` first bites at DS 511 (the grid skips 0.00). *Severity: blocker for R1-03/R3-07 acceptance.* (02 §6; intentional-diffs §7)
34. **A BP2 pressure read blocks the control loop 20 % of wall clock, and checks nothing.** `pressureSensor.h:35` does `delay(10)` every 50 ms; `stat` is computed and never read (a NAK is invisible); `requestFrom`'s return is discarded, so a short read converts **the previous sample** as if fresh. Also `counts_to_percentage` divides by full scale while `counts_to_bar` divides by the output span, so 10 bar reads as 90 %. *Severity: major.* (01 §4; intentional-diffs §10)
35. **HX711: unbounded spin loops plus a `static` deadline initialised on first call.** `HX711Scale.cpp:44,51` spin on `startMultiple` forever, and `HX711_ADC.cpp:135`'s `static unsigned long timeout = millis() + tareTimeOut;` is initialised once — so the dual-cell path's second `startMultiple` inherits a possibly-expired deadline. A port that armed its fault watchdog on the *first conversion* (the first Rust build did) reproduces the C++'s exact defect in new code: a cell that never speaks is never declared faulty, forever. *Severity: major.* (09 §23; intentional-diffs §10)
36. **The device had a foreign Rust firmware on it** (`v0.0.1-3-gfb0564a-dirty`, built by a clone not in this repo), with a *different live partition table* from the root CSV, and Wi-Fi credentials in its NVS. Any parity capture diffing `/api/wifi` or NVS must not commit them, and R0-02 must reconcile rather than restart. *Severity: major (containment).* (01 §10.1 🔴1)
37. **Two documentation claims in the branch's own skill were wrong and are corrected in place**: the USB bridge is a **WCH CH340** (VID `0x1A86`/PID `0x7523`), not a CP2102N; and the auto-reset circuit **is** present and working (5/5 first-try connects), contradicting the "may need manual BOOT+RST" warning. *Severity: minor, but it would have built a broken flashing workflow.* (01 §10.1 🔴2/🔴3; notes)
38. **R3-17 was a dependency deadlock**: it depended on R4-01, Gate 3 required every `HW: yes` R3 task to pass, and R4-01 depends on Gate 3. Renamed R4-01b. *Severity: minor (process).* (notes correction #15)
39. **Six plan-level errors found by adversarial review and fixed in the repo**, all in the same direction (stale counts): 18 states not 19, 96 registered params not 108, 10 fonts not 11, 21 `static_assert`s not 22, 33 suites not 50, ~28 kLoC not 19. Plus "the original ESP32 has no Bluetooth radio" was **false** — and that false belief is what made "drop the scales" look safe. *Severity: major (it changed a decision).* (notes corrections #1–#2; 06 R3-18)
40. **Self-contradictions to note:** (a) **09 has two §17s, two §18s, two §19s and two §20s** — the file was appended to rather than revised, so the first §17/§18 are factually wrong and carry in-file retractions; (b) 03's ADR still says the ESP32's USB cable is "a CP210x-class bridge" and 05 §3/SKILL §1 still say "CP2102N", both corrected elsewhere to CH340; (c) ADR-0004 is titled **"Proposed"** in 03 and the Openness table in 06 still lists scale support as an open question, while notes says "**Accepted** in practice"; (d) R1-07's "Decision: LEDC, 1 Hz" text remains in 06 under a table that is itself marked superseded by intentional-diffs #9; (e) 07 §1 calls flash the binding constraint while §8/§12 conclude **RAM** is; (f) 01 §3 keeps the "recommend: drop" scale paragraph directly beneath a callout that says it was superseded 2026-09-29; (g) 04 §5's ownership table still lists the watchdog owner as `main` while §3.4 requires it be moved into the control task; (h) intentional-diffs §5's heading ("heater is driven by LEDC") survives inside a section struck through as "superseded by #9". (09; 03; 05; 06; 07; 01; 04; intentional-diffs §5)

## 4. Verification strategy

- **C++ is the frozen parity baseline and is never modified or flashed**: `pio run -e esp32_usb` green at 1,546,240 B, `pio test -e native_test` 340/340 in 22–55 s; PlatformIO and Cargo coexist, PlatformIO is deprecated only at R4-10 and kept one release cycle for rollback (README; notes; 04 §9).
- **A 33-suite coverage map assigns every C++ suite an owner task and a safety path** — "a suite with no owner is a silent regression waiting to happen"; a suite decided not to be ported must have its row removed with a reason (06 coverage map).
- **Exhaustive reducer table:** 18 states × 46 events × 5 machine flavours = **4,140 pairs**, every pair reaching a named verdict, plus a 64-tick convergence drive — replacing C++ suites that turn out to test gMock plumbing and hand-written mock states rather than the real ones (notes R2-08; 09 §16).
- **Two-sided oracles against real C, not reimplementations:** the PID oracle compiles the **unmodified `PID_v1.cpp`** and replays identical sequences (scenarios A–C bit-identical, max |Δ| 0.0; D retained as the C++'s NaN; E quantifies the residual at max |Δ| = 1.0); the display oracle links the **actual U8g2 2.36.18 tree the firmware links** and requires **bit-identical** 128×64 framebuffers across eleven scenarios — with the scenario format implemented twice, once in C++ and once in Rust, on purpose (intentional-diffs §4; docs/display-parity.md).
- **Divergence ledger as machine-readable `ledger` blocks inside `intentional-diffs.md`**, each naming a heading in the same document so prose and ledger cannot drift; the runner exits non-zero on any diff the ledger does not explain, and a test proves a synthetic *undeclared* diff fails while a declared one does not (intentional-diffs; notes R1-08).
- **Structural actuator safety in the harness:** 12 of 17 scenarios would energise pump/valve/heater and are `dry_run` — the real reducer and real safety monitor in-process on the host with an `Actuators` that is a `Vec` of call names; `cc-parity` has no GPIO and no `cc-hal-esp32` in its tree, so nothing can reach a pin (10 §2; notes).
- **`actuator_safe` as the closing assertion of every scenario** — heater duty 0, pump off, both valves closed, latch *not* set — so a scenario that would have left a pump running says so even with nothing connected (10 §5).
- **Goldens with an explicit honesty section:** 48 committed P4 images plus an assertion on which `Stage` each case reaches, and a written list of what the goldens do **not** prove (they record the port, not the C++; `DrawTarget` unimplemented; SH1106 offset has no driver; the oracle is host-native U8g2, not Xtensa codegen) (docs/display-parity.md).
- **Compile-time safety invariants as tests:** adding a water-flow state without updating the whitelist must **fail to compile**; `RESOLUTION` and `CHOSEN_MAX_DUTY` tied by a `const` assert so reaching `Bits20` is a build error; a deliberately wrong pin fails to compile; `a LOW_TRIGGER` heater config is refused (04 §6; checklists §A; 06 R3-03).
- **Per-gate size report with attribution by crate and largest symbol**, `size-baseline.json` in the repo, `just size-check` failing on >10 % unexplained growth — which **did** fire and correctly failed the R3-09 + R4-01 gate at exactly +10.0 % (07 §4, §5, §11-final).
- **Host tests 900+, device tests 89 on real hardware** via `just test-esp32` (a gate that did not exist until R1-08's follow-up, whose absence had already let three device bugs ship) (notes).
- **Hardware validation is gated behind written, reviewed safe-test procedures** — boiler physically disconnected, machine in `PidDisabledState`, dummy load only, no brew/backflush/flush during a spike — and R1-07 steps 1–2 were **left un-run rather than claimed** because no scope was attached (06 R1-07; checklists §C; skill §2 rule 4).
- **An empty C++ baseline is treated as an error, not a skip**: `just parity` reports `BASELINE-MISSING` and exits 2, and "no baseline was fabricated" — an empty directory is the honest state, a directory of Rust observations labelled `cpp/` would be a lie the runner then confirms every run (06 R1-08; baseline/README.md).
- **Wokwi simulation** listed as the optional CI-level check (04 §8; 01 F34).

## 5. Migration sequencing

- **Phase 0 preconditions → Phase 1 feasibility spikes (Gate 1 flips ADR-0004 Proposed→Accepted) → Phase 2 portable domain (no hardware) → Phase 3 hardware abstraction → Phase 4 integration/provisioning/parity**, with a dependency graph and four gates (06).
- **Gate 1 is the riskiest ordering in the plan and is still un-passable**: it requires R1-01, R1-02, R1-03, R1-07 to pass *and* R1-08 to have produced a committed C++ baseline — and R1-08's capture is refused, so 13 scenarios report `BASELINE-MISSING`. The plan itself notes the ordering defect that put parity-baseline capture in Phase 1 while `scripts/parity/run.sh` was scheduled for R4-03 in Phase 4, making Gates 1–3 un-passable as written (06 R1-08).
- **Phase 2 before Phase 3 is deliberate and load-bearing**: the reducer, safety monitor, config schema and display layout are all host-testable, so the majority of the behavioural surface and safety paths S1/S2/S3/S5 are proven before a single pin is driven (04 §6, §8).
- **R4-01 is the critical path and is explicitly the most dangerous single ordering decision**: the 420-test `cc-machine` reducer is complete and heavily host-tested but **has never run on hardware** — the control task is a hand-rolled heuristic that acknowledges web commands and drops them, so there is currently **no state machine, no PID and no brewing on the device**; nothing after R4-01 can be trusted until it lands (README; notes).
- **Risk ordering deliberately keeps the C++ in production the whole way**, with the Rust added alongside and PlatformIO surviving one release cycle as a rollback path (04 §9; 06 R4-10).
- **Phase 3 is split so drivers follow the reducer**, with the `HW: yes` tasks gated individually and a hard rule that a target is not supported because it builds (`build-all` excludes S3/C6) (06 R3, R4-07/08 rule).
- **Phase 4 ends with a soak before the parity claim** (R4-05 24 h unattended, then R4-03 zero unexplained diffs) and R4-01b is separated from R4-01 purely to break the dependency deadlock (06; notes correction #15).
- **Rule: don't optimise before measuring** — R2-09 is a micro-benchmark of the pure reducer before any splitting of the control loop, and the tick-budget overrun must be fixed or recorded, never fixed by relaxing `TICK_BUDGET_MS` (06 R2-09; 09 §24).
- **Open decisions are parked with defaults** so Phase 2 is not blocked: SH1106 → drop and document; SSE → SSE via `EspHttpConnection::write`/`raw_connection()`; NVS encryption → no, parity; S3/C6 → no (06 open decisions).

## 6. Unique to this branch

- **A flash-dump "recovered oracle" that rewrote the plan.** A complete Rust firmware had already run on this board; the source is gone but a 4 MB `read_flash` dump survives, and its recovered strings, partition table, log tags and key list were mined for design decisions better than the plan's own — the deadman heartbeat, cross-parameter config validation, the `LOW_TRIGGER` heater refusal, fail-closed config load, the JSON-blob storage shape, and UART Wi-Fi provisioning. The plan was formally revised to adopt them (08).
- **Its strongest corroboration is a 6-byte delta:** the ported default config blob serialises to **2,077 bytes** against the lost firmware's logged **2,071 B** for a 98-key schema — treated as strong evidence the parameter shape is right (09 corroboration; 08 §3).
- **A deadman heartbeat adopted as a requirement, not an idea.** "Output held off until the supervisor beats" — the heater is gated by a latching software heartbeat, which drops it in the 500 ms interlock period rather than at a 5 s watchdog reset. The plan originally had no equivalent and relied on the watchdog (08 §4, §6; 06 R3-03).
- **The one self-imposed hostname divergence**, `test-cc-rust` over `silvia`, with the reasoning that during the migration the two firmwares share a network and are *not* interchangeable — plus the sharp distinction that `mqtt.password`'s identical `"silvia"` is a credential and must stay (intentional-diffs §12).
- **`std`'s own backtrace symbolisation measured and removed for −162,656 B** via `std/backtrace-trace-only`, with symbol-level evidence (148 → 0 gimli/addr2line symbols) *and* a measured on-board panic probe proving a crash is still diagnosable from raw PCs host-side — plus the trap that a `panic!` probe inline in `bring_up` lets LTO drop the whole bring-up (1,186,768 → 220,768 B), so the probe must be a spawned task (07 §9, §10, §13.1).
- **A whole size-budget narrative built around mbedTLS being a linker-level fact, not a code choice**, with the link-map reference chain (`libmqtt.a` → `libesp-tls.a` → `libmbedtls.a`; `libwpa_supplicant.a` → mbedtls) and the explicit statement that cutting WPA3/Enterprise is a product decision for a phase gate, not a size optimisation (07 §11).
- **The FP-in-ISR rule for the original ESP32, with a copy-pasteable `objdump` grep and the warning that a naive `.s` grep also matches `divn.s`/`un.s`/`moveqz.s`** — a hazard that is invisible in Rust source review because the source reads as integer arithmetic (09 §22).
- **The "the ISR rate is not the switching rate" derivation**, including the arithmetic of `div_param = (80e6 << 8)/(f · 2^bits)`, the `LEDC_IS_DIV_INVALID` bounds, why `Bits17` is the coarsest that works (period exactly 80,000,000 APB clocks), why `Bits20` is banned by a `const` assert, and a full self-correction of the earlier 100 Hz analysis including the errors in its own discarded table (04 §5; notes R1-07).
- **A documented two-sided display oracle with an unusually blunt "what this does not prove" section**, including the admission that the goldens record the port rather than the C++ and would faithfully protect a misreading of it (docs/display-parity.md).
- **The `dry_run` harness design that makes 12 actuator-energising scenarios runnable with no machine attached** — safety is structural (no GPIO, no `cc-hal-esp32` in the dependency tree) rather than a convention, with an explicit warning to keep it that way (10 §2; notes R1-08).
- **The insistence that a missing baseline is an error rather than a skip**, and the explicit reasoning that a directory of Rust-produced observations labelled `cpp/` "would be a lie that `just parity` then confirms on every future run" (baseline/README.md).
- **The "a target is not supported because it builds" rule wired into the tooling**, with `build-esp32s3`/`build-esp32c6` deliberately excluded from `build-all` and the C6 called out as deceptively easy (no compiler fork, but a different GPIO map, no GPIO 34–39 input-only block) (05 §4; 06 R4-07/08).
- **A skill written for agent execution rather than humans**, including the anti-patterns agents actually produce: `KEY=value` passed to `just` reaching `espflash` argv, `{{ fn(args) }}` in a justfile, a `cargo tree 2>/dev/null | grep -q` gate that fails **open**, a `wifi-reset` recipe that leaked the auth password into curl's world-readable argv, a text grep that matched `esp_idf_svc` but not the `esp-idf-svc` dependency name, a CI job with no `env:` block silently using the default ESP-IDF, and a flash dump with plaintext Wi-Fi credentials that must never be committed (notes corrections; 05 §6; 08 header).
- **A live "where the work actually is" honesty section** in the README and skill that names the critical gap (R4-01), the not-started set (OLED, OTA, Acaia BLE, ABP2 construction, `/ui` mount, telnet), and the deliberately-absent baseline — precisely because "several task IDs look complete from their description and are not" (README; skill §0).
- **The rule that the two image-size recorders must be run from a tree whose ELF is the build being claimed**, after a 1,197,712 B record was written from a stale ELF and had to be taken back out, and the cross-check that every number was reproduced byte-for-byte in a clean `git worktree` because another session had uncompilable work in flight (07 §13.1).
- **A separation of "measured", "derived from vendor source" and "guessed" as first-class labels** — every unrun hardware test is named as unrun, every acceptance criterion that is unverified is left unverified, and the TSIC-306's synthesised-waveform test is explicitly stated to prove the arithmetic and nothing about a real sensor (02 confidence key; 04 §5; 06 R1-07; intentional-diffs §7).
