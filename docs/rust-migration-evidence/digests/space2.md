## 1. Target architecture (as this branch proposes it)

- **Platform**: bare-metal `esp-hal` 1.2.2 + `embassy` (`esp-rtos` 0.4.0, `embassy-executor` 0.10.0), **no ESP-IDF**, `no_std` everywhere below the BSP. Explicitly rejected `esp-idf-hal`/`esp-idf-svc` (docs/rust-migration/decision-record.md).
- **17-crate workspace**, dependency direction strictly downward, enforced mechanically by `tools/check-deps.py` in CI: `domain`, `hal-traits`, `onewire`, `ds18b20`, `drivers-{pressure,scale,tsic}`, `display`, `http`, `storage`, `config`, `app`, `board-profiles`, `bsp-<board>`, `fw` (docs/rust-migration/architecture.md §2).
- **Execution model: one executor, no network task.** `embassy-net` runs on the executor, so a slow HTTP client cannot preempt the control loop (docs/rust-migration/architecture.md §1).
- **Seven tasks**: `control` (1 ms tick / 10 ms PWM window), `sensors` (400 ms temp, 50 ms pressure, 200 ms tank, 100 ms scale), `safety` (every control tick), `display` (100 ms), `net` (event driven), `provision` (event driven), `logger` (30 s heartbeat). `control` and `safety` are deliberately separate so interlocks cannot be starved (docs/rust-migration/architecture.md §1.1).
- **Actuator ownership is a type-system invariant**: a single `Actuators` struct owns the pump/valve/heater/solenoid pins and exposes only `command(Command)` and `force_off()`; pins are *moved* into it at startup so no other handle exists (docs/rust-migration/architecture.md §1.2).
- **No locks in the control path**; cross-task state is owned by exactly one task and communicated over `embassy_sync::channel` + `heapless` bounded channels that drop the oldest sample on overflow (docs/rust-migration/architecture.md §1.2–1.3).
- **Hardware abstraction is a trait set**: `Actuators`, `TemperatureSensor`, `PressureSensor`, `Display`, `Switch`, `Scale`, `Storage`, `ProvisioningTransport`, `Clock` in `hal-traits`, with `RecordingActuators` as the fake used by every control test and by the on-device `mock-actuators` build (docs/rust-migration/task-list.md T-03).
- **State machine lives in `clevercoffee-domain`**: `State`, `Transition`, `Pid`, `SensorReading`, `BrewPlan`, `BackflushPlan`, `StandbyPlan`, timing constants, and `State::may_hold_water_valve_open()` as the *single* valve allow-list (docs/rust-migration/architecture.md §2, defects-register.md D56).
- **Heater**: hardware PWM from the MCPWM peripheral at the C++ firmware's 10 ms window and 0–1000 duty — so the machine has **no heater interrupt at all**; `Stage::HeldOff` holds the heater off if the PWM peripheral will not start (defects-register.md D59, task-list.md T-13).
- **Config persistence**: a custom 4 MB partition table (`nvs` kept unused for the ROM bootloader, `otadata`, two 1.5 MB `ota_0`/`ota_1` slots, a 64 KB versioned `config` region, an 832 KB `assets` region, `coredump`), with a two-slot A/B `config` region carrying magic `"CCFG"`, `format_version`, wraparound-compared `slot_generation`, `payload_length`, CRC-32 and a 16-byte SHA-256 prefix, postcard payload, read-back verification on write (docs/rust-migration/architecture.md §3.1–3.2).
- **Clean break on storage**: the C++ NVS layout (FNV-1a hashed keys, `config` + `maintenance` namespaces) is not carried over; the only bridge is config JSON export → flash over USB → import (docs/rust-migration/decision-record.md, `.agents/skills/esp32-rust-migration/SKILL.md` §9).
- **HTTP is owned**: `clevercoffee-http` is a minimal HTTP/1.1 server over `embassy-net` (routing, SSE, chunked bodies, `Accept-Encoding` negotiation, static assets from the `assets` region); handlers are pure functions from parsed request to response with no network or flash access, which is what makes the API host-testable (docs/rust-migration/architecture.md §4).
- **Sync-server-over-async-socket bridge**: `app::net::Bridged` — a pump task moves bytes between an `embassy-net` socket and two bounded rings; a stalled client fills a ring and is dropped (HANDOFF.md, defects-register.md D39).
- **Boot order is safety-ordered**: clocks → actuators driven to their inactive level *before anything else* → config region read/CRC → sensor probe (missing sensor = fatal for the heater) → network last → provisioning channel opened regardless of network state (docs/rust-migration/architecture.md §1.4).
- **Board variation is a compile-time feature set**: `domain`/`hal-traits`/`board-profiles`/`config` vary by nothing; pin maps are plain host-testable data in `board-profiles`; `bsp-<board>` holds the `Board` impl; exactly one of `board-esp32|esp32s3|esp32c6` and one of `prov-uart|prov-usb-cdc`, with every wrong combination turned into a `compile_error!` in `crates/fw/src/checks.rs` (docs/rust-migration/architecture.md §1.7).
- **USB provisioning** replaces NVS + the Wi-Fi captive portal: a line-oriented `KEY value` protocol with `OK <code> <token>` / `ERR <code> <reason>`, length-prefixed base64 chunks with CRC-32, on-device validation against the same schema table the API uses, and no secret ever echoed (docs/rust-migration/architecture.md §6).

## 2. Key decisions and their rationale

| Decision | Chosen | Why | Rejected alternatives |
| --- | --- | --- | --- |
| HAL / platform | `esp-hal` 1.2.2 bare metal + `embassy` | Machine-enforced per-chip CI matrix in `.github/chips.json`, per-chip HIL runners incl. radio; auditable single-executor concurrency model for a safety-critical ISR-driven loop (decision-record.md) | `esp-idf-hal`/`esp-idf-svc`: self-reports "missing HIL tests" and lag behind stable IDF; lwIP + RTOS |
| Wi-Fi + networking | `esp-radio` 1.0.0-beta.1 + `embassy-net` on smoltcp, on the executor | 99 KB app image vs a 2.5 MB lwIP/IDF hello-world; verified in `spikes/stack-smoke` for all three chips | AsyncTCP's separate network task, which is what caused D01/D06/D07 |
| HTTP server | Own `clevercoffee-http` (~600 lines + ~800 lines of host tests) | No `esp-rs/esp-http-server` (404); ecosystem crates are tiny/low-adoption; `picoserve` has no track record on this hardware; also removes the largest untested C++ subsystem (decision-record.md) | `picoserve`, `nanofish`, `nanooctopus`, `peaweb` |
| 1-Wire / DS18B20 | Own `onewire` + `ds18b20` crates (~300–500 lines) | Only end-to-end crate is `ds18b20` 0.1.1 (2020), pins `embedded-hal` 0.2.3 while `esp-hal` 1.x is 1.0, and is a GPIO bit-bang with no hardware backend; `esp-hal` has no 1-Wire module (decision-record.md) | `ds18b20` 0.1.1 + `one-wire-bus` |
| "S3/C6 have a 1-Wire peripheral" | **Refuted** — bit-bang on every chip | C6 datasheet v1.5 peripheral table lists no 1-Wire controller; S3 datasheet not retrieved, so S3 left `unverified` on this point (decision-record.md) | Hardware 1-Wire peripheral (asserted in the task brief) |
| Temperature sensors | Both DS18B20 and TSIC 306 kept; `hardware.sensors.temperature.type` selects at boot | User decision 2026-09-29; `ZACwire` has no Rust equivalent but the bench has a DS18B20 so the TSIC path is build-verified only (decision-record.md) | Drop the TSIC (the plan's original proposal) |
| OTA | **Kept in all four paths**, corrected not deleted: HTTP upload, URL download, espota, plus a new USB path; two 1.5 MB slots via `esp-bootloader-esp-idf` 0.6.0 `OtaUpdater` | User decision 2026-09-29 ("remove OTA only if space becomes a problem"); space is not a constraint — 99 KB image vs 1.5 MB slot | Deleting the two HTTP OTA routes (original plan, on D16 SSRF + D17 unauthenticated grounds) |
| OTA gating | Every path refuses unless the machine is idle, then calls `Actuators::force_off()` | The direct fix for D01 (OTA left pump and valve energized) | Preserving the C++ behaviour of allowing OTA mid-brew |
| Config storage | Custom versioned CRC-protected binary `config` region (2 × 32 KB A/B) | No Rust NVS binding; the NVS-image generator is an ESP-IDF Python module whose input format was unverified and which puts credentials in a plaintext host file (decision-record.md) | ESP-IDF `nvs_partition_gen.py` + `espflash write-bin`; carrying the C++ NVS layout over |
| Provisioning transport | Line-oriented text protocol: UART0 on ESP32, USB Serial/JTAG CDC on S3/C6, behind one `ProvisioningTransport` trait | ESP32 has no native USB; `esp-hal` exposes UART as an ordinary peripheral and the S3/C6 USB Serial/JTAG peripheral directly; identical protocol everywhere so one host script (decision-record.md) | USB CDC everywhere (unavailable on ESP32); prebuilt NVS image + `write-bin` (secret on the host); custom binary region + `write-bin` |
| Wi-Fi captive portal | **Dropped** | USB provisioning removes the need; `WiFiManager` blocks the main loop for up to 60 s at boot. User decision 2026-09-29 (decision-record.md, inventory.md P7) | Keeping `WiFiManager` |
| Wokwi simulation | **Dropped** | Wokwi runs the PlatformIO build; the Rust firmware cannot run there. User decision 2026-09-29 (inventory.md P8) | Keeping a PlatformIO-based simulator alongside |
| Acaia Bluetooth scale | **Deferred** | Dead code in the C++ firmware (`setScaleSensor()` has no call sites), so zero parity pressure; a BLE stack swap plus a vendor protocol is 600–1000 lines with no test bench (inventory.md P3) | `TrouBLE` + own Acaia client |
| ESP32-C6 feature set | **3 indicator LEDs and the 2nd HX711 cell disabled** by the `board-esp32c6` feature | 17 pins needed, only 14 usable on the C6-DevKitC-1 (23 exposed, less USB D-/D+, less the module's 6 SDIO flash pins, less the RGB LED). User decision 2026-09-29 (board-pinouts.md §3) | An IO expander (rejected by the user; would also leave 10 ms heater PWM over I2C unresolved); a different board |
| `no_std` vs `std` | `no_std` for everything below the BSP; `std` only in host test crates and the host provisioning tool | Bare-metal, smallest image (99 KB), one async model; `crates/app/tests/*.rs` are separate crates precisely so `format!` works there (HANDOFF.md) | `std` via `esp-idf-svc` |
| Watchdog | Fed by the `safety` task every 50 ms, in its own task | A hang in control/display/network still trips it, and a long control-path block is no longer a false trip (architecture.md §1.3) | C++'s single feed at the top of `loop()` |
| TLS | None | Local network; the C++ firmware had SSL disabled (`platformio.ini:26`) (architecture.md §4) | Adding TLS to the device |
| Secret storage at rest | Plaintext in the config region, documented as a limitation | Original ESP32 has no secure storage and S3/C6 eFuse would be a separate project; the region is one self-describing blob so NVS encryption is addable later (architecture.md §6.3) | NVS encryption, eFuse |
| Partition size | Two 1.5 MB app slots (not the C++'s 1.625 MB) | Config and assets are explicit regions rather than sharing one `spiffs` partition, and 1.5 MB is far more than needed (architecture.md §3.1) | Larger slots / growth on the 8 MB S3 and C6 |
| Verification standard | Four levels: `repo-verified` / `build-verified` / `device-verified` / `needs confirmation`; only `device-verified` counts as fully supported | A capability that builds is not a capability that works (verification-levels.md) | A looser standard |

## 3. Pitfalls, gotchas and hard problems discovered

**Safety-critical C++ behaviour that is accidental and must NOT be preserved**

1. **Disconnected temperature sensor is never detected → PID saturates at 100 %.** `tryGetValue()` returns `SENSOR_NOT_READY` for *every* failure mode and the coordinator treats it as "still in progress"; `startRead()` re-arms every 400 ms so the 1000 ms timeout can never fire; `cachedTemperature_` stays at its initial `0.0`, which is in range, so the emergency-stop manager sees no fault either. `SENSOR_ERROR` is unreachable for temperature and `updateTemperature()` (which holds `bad_readings_`) has no call sites. **severity: blocker** (defects-register.md D03, inventory.md §11).
2. **`heaterEnabled_` is never set, so every heater shutdown path is inert.** `enableHeater()` has zero call sites; `disableHeater()`, `safeShutdown()`, `disableAllHardware()` and the partial-init cleanup all early-return on `if (!heaterEnabled_)`. The heater is driven only by the 10 ms ISR. **blocker** (defects-register.md D02).
3. **An active OTA leaves the pump and valve energized.** `LoopManager::update()` returns early before the state machine, `valveSafetyShutdownCheck()` and the PID; `otaPrepareHardware()` disables only the heater timer, and that `disableHeater()` is a no-op because of D02. `beginSession()` is additionally called from the network task. **blocker** (D01).
4. **Hot water pumps with the three-way valve shut.** The valve interlock whitelists brew / manual flush / backflush states, but the hot-water dispense runs *inside* `PID_NORMAL` and `STEAM_RUNNING` with no state of its own, so the check closed the valve every tick while the pump kept running — and the heater is on throughout. Verified against the real `include/clevercoffee/handlers/BrewHandler.h`. **blocker for the feature, major for safety** (D56, found *while porting*, not in the original register).
5. **`setHeaterDuty` was a no-op: every heater duty was 100 %.** The PID's 0–1000 duty went to a variable nobody read, while the state machine's actuator command drove the pin high. The loop still converges via the integral term, so it is invisible in normal operation and obvious on a bench; a machine whose heater cannot be turned down is safety-adjacent. **blocker/major** (D59, found while porting).
6. **Three conflicting emergency-stop thresholds coexist**: a `GlobalTypes` constant of 145, a `Temperature.h` pair of 145 and 120, and the live config default of 150 with a 100 clear; `testEmergencyStop()` is dead code. **major** (D33).
7. **The PID gains configured for brewing are always overwritten by the brew-detection gains.** `calculateDerivedValues()` computes `aggKi`/`aggKd` from `pid.regular.*`, stores them, then immediately recomputes from `pid.bd.*` and stores over the top ("mapped to aggKi/aggKd for now"). In the shipped `config.json` the BD `tn` is 0, so **the brew PID has no integral action at all**. **major** (D45).
8. **The integrator limit is hardcoded 55 at boot while `config.json` sets 75**, and the configured value only takes effect on the first state transition. **minor–major** (D46).
9. **The Arduino-PID input filter starts at 0**, so the first `Compute()` sees `dInput ≈ (1-α)·input/dt ≈ −14 000` counts; output clamps to 0 and the heater does not start for a full sample period — a symptom (machine appears not to heat) that reads as a sensor fault. **minor, but a diagnostic trap** (D47).
10. **The backflush *flush* phase closes the water valve, so the group cannot drain**, while the same file logs "flushing into drip tray" and `valveSafetyShutdownCheck` explicitly whitelists `BACKFLUSH_FLUSHING` as a state that may hold the valve open. The C++ contradicts itself about what the phase is for. **major** (D49).
11. **The "safe mode" performs no hardware action.** `enterSafeMode`, `exitSafeMode`, `disableWaterOperations`, `enableWaterOperations` are log-only stubs, and `SensorErrorState::onEntryImpl` calls `enterSafeMode()` believing it disables hardware. **major** (D21).
12. **`BackflushFillingState::update()` does not re-assert its hardware state**, so if the tank latch or the interlock turns the pump off mid-fill it never comes back until the fill times out. **major** (D19).
13. **`cleanupPumpAndValve()` never closes the steam valve** (`closeWaterValve()` early-returns on `STEAM_OPEN`). Latent only because `openSteamValve()` is never called. **minor** (D20).
14. **C++ pump run-time limits do not exist**: `PumpTimer::isExpired()` returns false when not running and neither `start()` nor `stop()` is ever called, so both `checkPumpTimeout()` bodies are unreachable — the advertised 5-minute brew and 60-second hot-water limits are fiction. **major** (D09).

**Hardware / timing / ISR / electrical**

15. **The 10 ms heater ISR calls flash-resident code.** `onTimer` is `IRAM_ATTR` but `Relay::on/off()` and `GPIOPin::write()` are ordinary `.cpp` functions, and `Relay.h:17-25` explicitly *claims* they are ISR-safe; during a flash erase the icache can be bypassed → illegal-instruction panic. The ISR also re-programs an already auto-reloading alarm every tick. **major** (D05).
16. **The 10 ms ISR reads a non-atomic `double` written by the PID.** Formally a data race; Xtensa's aligned 8-byte access makes tearing unlikely but the compiler is free to tear it. **major** (D18).
17. **The pressure read blocks the main loop for 10 ms every 50 ms** — 20 % of loop wall-clock whenever pressure sensing is on, and both the class comment and ADR 0002 describe the path as non-blocking. **major** (D08/D55).
18. **The I2C bus runs at the Arduino default 100 kHz** (`Wire.setClock()` never called) and the display is in U8g2 full-page mode, so every 10 Hz render pushes 1024 bytes and blocks ~90 ms — exceeding the project's own 100 ms slow-loop threshold. **major** (D31).
19. **Four panel switches sit on ESP32 input-only pins 34/35/36/39 with `pinMode(INPUT)` and no internal pull**, so the board *must* supply external pull-ups or pull-downs. This is a hardware requirement, not a firmware choice, and it does not carry to S3/C6 (no input-only pins there). **major, hardware** (board-pinouts.md §4.1, inventory.md §2.3).
20. **The heater relay sits on GPIO2, a boot-mode strapping pin, and is driven late** — relays are created and driven off only after logger, LittleFS, NVS, I2C and the display are up, so the strapping sample is not guaranteed correct. The steam LED is on **GPIO1, which is UART0 TX**. Both are moved in the new map (heater → GPIO4, steam LED → GPIO21, I2C SCL → GPIO15, itself a strapping pin that happens to be correct only because I2C idles high). **major** (D36, board-pinouts.md §5.1).
21. **The ESP32-C6-DevKitC-1 does not have enough pins**: 23 exposed, 14 usable, 17 needed. The vendor guide even contradicts its own J3 table ("all available GPIO pins except the SPI bus for flash are broken out") while listing all six SDIO pins. **blocker for feature parity on C6** (board-pinouts.md §3).
22. **The ESP32-S3-DevKitC-1 v1.0 and v1.1 differ**: the RGB LED is GPIO48 on v1.0 and GPIO38 on v1.1, so a pin map written against one hits the LED on the other. **major, hardware** (board-pinouts.md §4.4).
23. **A bit-banged 1-Wire bus cannot be done from an async task without blocking the executor** — "which is the shape of D05". The DS18B20/ABP2/HX711 drivers are written and host-tested but *nothing constructs them in the firmware* (parity-report.md §6).
24. **Multi-drop 1-Wire ROM enumeration is unverified**: the simulated bus cannot model several devices driving the line at once. Honest framing: a real machine has one sensor, so it is a gap in the tests rather than a path the firmware takes (task-list.md T-09 "Not verified", HANDOFF.md).
25. **Relay coils must not be powered from the dev board's 3.3 V rail**; the ESP32 datasheet asks for ≥500 mA and three relay coils plus a heater SSR exceed it (board-pinouts.md §7). Outside what the migration can verify.
26. **The ABP2 frame is 12 bytes, not 7.** The C++ reads seven bytes and builds its temperature count from `data[6] + data[5]·256 + data[4]·65536`, mixing the *second word's status byte* with two data bytes; it also never checks either status byte for a diagnostic fault, and converts out-of-span counts into negative pressures the over-pressure logic accepts. **major** (D54).
27. **The scale calibration is a *divisor*, its range includes zero, and the negative half is legitimate** — the shipped `config.json` has −1750.05 / −1685.21 because an inverted load cell really reads negative. The range cannot be tightened to exclude zero without excluding real devices, so the port adds a separate `forbid_zero` flag instead. **major schema landmine** (D52).

**Config-schema and API-contract landmines**

28. **The exporter wrote keys its own importer rejects.** It emitted each parameter's *full dotted key as a leaf name inside its group object* (`"pid": {"pid.regular.kp": 50.0}`) while the import format nests. Sixteen keys per real export named parameters the schema does not have — and because the port rejects unknown fields (deliberately, D13's family), **every export the port produced was refused by its own importer**. A comma-state bug (`{,`) in the first attempt was caught only by the round-trip test. **blocker for the migration path** (D57, found while porting).
29. **`format_version` was written by the exporter and rejected by the importer.** The importer resolved it to the dotted path `format_version`, missed the schema, and rejected it as unknown — so **every real C++ export, the only migration path this port offers, was refused outright**. It survived two review passes because the repo's own `config.json` happens not to carry it. Fixed by recording it on `ResolvedDoc` and refusing an unread version *by name and in full, before any field is looked at*. **blocker** (D58, found while porting).
30. **Import is non-atomic and reports false success**: parameters are applied and committed one at a time, and the function returns `updatedCount > 0`, so 5 valid of 96 produce HTTP 200 "Configuration validated and applied successfully." **major** (D13).
31. **Range validation exists on `set()` but not on the NVS load path** — a corrupt or hand-edited blob loads straight into live control state including setpoints and PID gains. **major** (D11).
32. **`safety.emergency_temp` / `emergency_hysteresis` are consumed but never registered**, so they are never persisted, exported, imported or returned by `/api/parameters`, and are always the compiled default 150/5. A user who lowers the emergency threshold is silently ignored. **major** (D12).
33. **Four plaintext secrets are exported verbatim** from `GET /api/config`, `/api/config/download`, `/api/parameters` and `/api/nvs-debug`, with CORS reflecting any origin and credentials allowed; and the shipped defaults are real credentials (`mqtt.password` = `silvia`, `system.ota_password` = `otapass`). **major** (D14, config-export-schema.md).
34. **The auth middleware never calls `setAuthType()`**, so `allowed()` returns true for every request — including `/api/factory-reset`, `/api/restart`, `/api/wifi-reset` and all four OTA routes, even with `system.auth.enabled` set. **major** (D10).
35. **`docs/api/openapi.yaml` disagrees with the shipped code in 26 places**: a documented `POST /api/config` that does not exist, a `/api/scale/calibrate` that never existed, wrong field names on six routes, wrong request/response shapes, `/api/ota/url` documented as 200 when it is 202, a false claim that config upload restarts the device, and **no `securitySchemes` at all**. **major** (D34, api-contract.md §Spec drift).
36. **The two repository JSON files disagree with each other and with the code**: different temperature sensor type (TSIC vs DS18B20), different scale type, different calibrations (−1750.05/−1685.21 vs 1000.0/1000.0), different known weights. And the root `config.json` is *not* the LittleFS seed file — `seedFromLittleFS` reads `/config.json` from an image built from a gitignored `data/`. **major** (config-export-schema.md reconciliation table, inventory.md §9).
37. **There is no schema version marker anywhere in the C++ firmware**; the only marker is a `_seeded` boolean in NVS. NVS keys are 9-character FNV-1a hashes of the dotted name. Flat dotted keys are rejected only at the top level, so `{"pid": {"regular.kp": 5}}` passes the check and is then silently ignored. **major** (config-export-schema.md).
38. **String fields have no length limit and the constants are dead**: `isValid` returns true for every string and all eight `*_MAX_LENGTH` constants are unreferenced; `CONFIG_REFERENCE.md`'s lengths disagree with `defaults.h` on five fields. **minor–major** (D23).
39. **Minor-but-nasty API behaviours**: `/api/setpoint` validates against an ad-hoc 0–150 range, applies it live, and only then calls `set()` whose real bound is 20–110 with the result discarded as `(void)` (D24); `POST /api/parameters` silently skips empty values so a string cannot be cleared (D25); the parameter filter maps `hardware` to a section that does not contain the hardware params and `other` to display (D26); importing a double routes through Arduino `String(double)` so `0.005` becomes `0.01` (D27); `/api/pid` returns 200 with a value it did not apply (D28); `/api/temperatures` sends error bodies with 200 (D15); `/api/ota/url` fetches any URL with no scheme or host allow-list and the firmware variant has no extension check at all (D16).

**Memory, flash and budget pressure**

40. **1-Wire, pressure and display must not sleep, and the display must not flush whole pages** — the port's rules are that no driver sleeps and the framebuffer diffs against the last flushed frame (an extra 1 KB, static) so an unchanged re-render sends nothing (D31, D55, task-list.md T-12).
41. **PSRAM is absent on the original ESP32** (`diagram.json:11`), and the log ring is a fixed 4 KB allocated at boot, the provisioning handler owns a 32 KB response buffer so `/api/parameters` does not leak one per request, and the HTTP layer must cap request size and header count because "an unbounded allocation on an embedded target is an OOM" (compatibility-matrix.md, HANDOFF.md, task-list.md T-07).
42. **Logger nesting can overflow the 8 KB loop-task stack** — ~576 bytes per nested `LOGF` plus `vsnprintf`, and states log from entry, exit, update and transition checks (D39).

**Toolchain and process gotchas that actually cost builds**

43. **`just espup-install` fetches an x86-64 `espup` binary; the host is aarch64, so it exits 126 and the `esp` rustc fork is never installed.** `just check-fw esp32`/`esp32s3` therefore *cannot run*, and `mise exec -- just check` fails at its first recipe because `rust-toolchain.toml` pins the `esp` channel and every bare `cargo` fails. Host work needs `cargo +stable`. **blocker for the stated verification plan** (HANDOFF.md, compatibility-matrix.md).
44. **Cargo unifies features across a `--workspace` build**, so including the `bsp-*` crates enables three chips at once and fails inside `esp-metadata-generated` with a duplicate-macro error. Host jobs and clippy must exclude exactly the four chip crates. **major** (tooling.md, architecture.md §2).
45. **`build-std` must be set per recipe, not in `.cargo/config.toml`** — a global `build-std` also applies to host builds and collides with the host's prebuilt `core`. **major** (tooling.md).
46. **HAL API drift cost build cycles** and is recorded verbatim: `esp_rtos::start` takes a second argument; `I2c::new(i2c, config)?.with_sda(pin).with_scl(pin)` puts the pin setters on `I2c`, not `Config`; `embassy_net::new(driver, config, &mut resources, seed)`; the USB peripheral is `USB_DEVICE`, not `USBTMC`, and the module is under `usb`. **minor** (tooling.md).
47. **The mise `ubi` backend fails against espflash releases** ("could not find any files matching [espflash*]"), so the `http` backend pins the exact x86-64 asset by sha256 — which pins the host architecture and makes macOS/aarch64 a manual edit. **minor** (tooling.md).
48. **The log transport follows the board, not the operator's port choice** — on S3/C6 logs land on the native USB port even when provisioning runs over the UART bridge, because Cargo allows one version of a crate per build. **minor, unfixable-as-designed** (tooling.md).
49. **Three defects were found by the porting host tests, not by review**: service mode was expressed as "the PID is off" in the transition input, so starting provisioning or an OTA ejected the machine from whatever it was doing and lost the brew; the emergency stop was evaluated on the *filtered* temperature, so a genuine over-temperature took six seconds to move a fifteen-sample mean far enough to trip; and a sensor fault was initially routed into the *latched* emergency stop, turning a recoverable fault into a machine that needed unplugging. **major** (HANDOFF.md, task-list.md T-14).
50. **The domain test asserted the wrong direction and hid D56.** The port's interlock test originally asserted *equality* between the states that command the valve and the states allowed to hold it — exactly the assertion that would have concealed a missing state. The fix asserts only the safety direction: a state that commands the valve must be allowed to hold it (D56).

## 4. Verification strategy

- **Four-level evidence standard** (`repo-verified` / `build-verified` / `device-verified` / `needs confirmation`), with the rule "raising a level requires the evidence named, in the same commit as the claim" and "a capability that compiles is not a capability that works" (docs/rust-migration/verification-levels.md).
- **Capability spikes as the evidence substrate**: `hal-smoke` (HAL init, executor, timer), `stack-smoke` (flash, partition table, I2C, UART0, Wi-Fi via `esp-radio`, linked `embassy-net`), `usb-smoke` (USB Serial/JTAG CDC async channel) — all built for all three targets; plus `espflash save-image` turning a 2 571 412-byte ELF into a 99 728-byte image at 0x10000, and the `just _assert-chip` flash guard (verification-levels.md, compatibility-matrix.md).
- **Host tests as the primary behavioural evidence**: 613 workspace tests plus 55 in the provisioning tool, all green, run under `cargo fmt --check`, `clippy -D warnings`, `tools/check-deps.py` and `tools/check-secrets.py` (HANDOFF.md).
- **Recording-fake whole-machine scenarios**: 21 scenarios run against `RecordingActuators` asserting the *exact actuator command sequence* — normal brew, abort in pre-infusion, abort in the pause, manual flush, backflush, tank emptying mid-brew, emergency stop from twelve states, standby/wake, sensor fault + recovery delay, unfed watchdog, stuck switch past the pump deadline (task-list.md T-14).
- **`mock-actuators` build feature** that *removes* real GPIO construction (verified by asserting the mock build's binary has no GPIO output) so a bench run can exercise the entire control path, the API and the config import with nothing energized (architecture.md §1.6, task-list.md T-03).
- **Pixel-level display verification** on a host framebuffer: every template × every state × three languages with a zero clip count, no overlapping rows, numeric fields identical in width when 9→10, bar and label sharing a midline; physical rendering deferred to T-21 (task-list.md T-12).
- **Config round-trip and fixture tests**: the repository's own `config.json` must import with zero unknown/rejected/clamped, `docs/example_config.json` must fail with exactly one unknown field named, and an export must parse through the same importer with zero unknowns — the test that caught D57 and the `{,` bug (task-list.md T-06, defects-register.md D57).
- **Storage fault-injection**: clean boot, one corrupt slot, both slots corrupt, torn write leaving the older slot intact, generation wraparound, one-byte-too-long payload, unfittable length, unreadable version in both directions (task-list.md T-05).
- **API route tests**: 31 tests over all thirty routes asserting exact status codes and body shapes, including the 401 the C++ never produced, the 409 while brewing, the URL allow-list, the extension check, redaction, and a "no handler contains an await" check run against the crate's own source (task-list.md T-16).
- **Parity report as a formal artefact**: every C++ behaviour with a row of `pass` / `fixed` / `deviation` / `gap` / `unverified`, each naming the test that is the evidence; four deviations with reasons, six gaps in close-order, and an explicit list of the rows that cannot close without hardware (parity-report.md).
- **`config_rt` coverage test**: the config schema has 99 parameters but the machine has ~30 fields, so a test fails when a parameter is *neither read by the machine nor listed as inert* — the mechanism that catches "a setting that looks live and is not" (parity-report.md §4, task-list.md T-14).
- **Known-unknown table**: every unverified claim is paired with what would settle it, from "the DS18B20 datasheet or a measured conversion" to "the part marking, from the user" for the ABP2 variant (verification-levels.md).
- **Agent-executed protocol**: `SKILL.md` mandates running the full six-command validation set before committing, self-reviewing the diff for a secret / leftover TODO / `unwrap()` in firmware / a blocking call in a handler / an `.await` in the control path without a timeout, and **"if validation fails three times, or the hardware is unavailable, make no success commit"**.

## 5. Migration sequencing

- **Seven phases, dependency-ordered**: Phase 0 foundation (T-01 workspace+CI+guards, T-02 domain, T-03 HAL traits+mock, T-04 config schema); Phase 1 storage and provisioning on host (T-05 config region, T-06 import/export, T-07 HTTP, T-08 host provisioning tool); Phase 2 drivers (T-09 onewire/DS18B20, T-09b TSIC, T-10 ABP2, T-11 HX711, T-12 display); Phase 3 board support + firmware (T-13); Phase 4 application (T-14 control tasks, T-15 provisioning device side, T-16 web API, T-17 MQTT/HA, T-18 telnet); Phase 5 parity and migration (T-19 device import, T-20 parity, T-21 display on device); Phase 6 removal (T-22 delete the C++ tree).
- **The gating rule that shapes everything: T-22 (delete `src/`, `include/`, `lib/`, `test/`, PlatformIO) is blocked behind every parity gate in T-20 passing**, and HANDOFF.md states flatly that T-22 "should not [start]: its prerequisite is a parity gate that cannot pass". The C++ tree is a live rollback path.
- **Parity scope is explicitly bounded**: functional, control and API behaviour only; storage format, partition layout and OTA are out of scope by design, and deviations that are defect fixes are exempt (task-list.md).
- **Riskiest ordering identified by this branch**: the *hardware* ordering — T-09, T-11, T-12, T-13, T-14, T-15, T-16, T-17, T-18, T-19, T-20, T-21 all need a board, and only T-01–T-08 and T-09b do not. The stated next action is therefore not a task but a toolchain: "get a chip toolchain and compile the board crates", because the remaining risk is ~400 lines of `esp-hal` glue in `crates/bsp-*` and `crates/fw` written against the HAL's source but never fed to a compiler (HANDOFF.md).
- **Riskiest second ordering**: **display before device** — T-12 is sized 1200–1800 lines because the C++ U8g2 font metrics "cannot be read from this repository", so the port ships a new 5×7 table at two integer scales and "every layout is verified against *its own* metrics". Physical appearance is unverified until T-21 (parity-report.md §5).
- **Riskiest third ordering**: **the C6 pin finding landed mid-plan and forced a feature reduction on one board** while ESP32 and S3 kept the full set; the resolution is a compile-time capability the shared logic already handles, so no logic changes, but it is a product decision taken by the user rather than by the design (board-pinouts.md §3).
- **Sequencing discipline in the process itself**: "a task either researches or implements, never both"; a research task produces a document and an implementation task does not go read upstream source; a neighbouring improvement goes in the report, not the diff; and when reality contradicts the design, architecture.md and the task list are updated in the *same commit as the code* (SKILL.md §2).
- **Phase gates are hardware-inclusive**: at the end of each phase, run the full validation set for every target, flash the bench device in mock-actuator mode, update compatibility-matrix.md, and report the phase result *including everything unverified* (SKILL.md §7).
- **Removals were deferred, not deleted**: Acaia BLE scale (dead code, no parity pressure), Wi-Fi captive portal (blocked the loop 60 s), Wokwi (PlatformIO-only), and the HTTP/URL OTA routes — the last of which was proposed for deletion and *reversed* by the user (task-list.md "Deferred and dropped" table).

## 6. Unique to this branch

- **The register was extended by defects found *while porting*, including two that would have destroyed the migration path itself.** D57 (the exporter wrote dotted keys as leaves, so every export was refused by its own stricter importer) and D58 (`format_version` rejected outright, so every *real C++ export* — the only file a migrating user has — was refused) were found only because the port tightened validation; both survived two review passes because the repo's own `config.json` lacks the key. D59 (`setHeaterDuty` was a no-op, every duty was 100 %) and D56 (hot water pumped with the valve shut) were also found during the port (defects-register.md, HANDOFF.md).
- **A test that asserted the wrong direction and hid a safety bug**, now fixed to assert only "a state that commands the valve must be allowed to hold it" — with the explicit argument that equality is "exactly the assertion that would have hidden this" (D56).
- **Hardware PWM replaces the heater ISR entirely** — "the D05 shape removed rather than documented", with `Stage::HeldOff` holding the heater *off* rather than driving the pin, on the reasoning that a machine that does not heat is noticed and a machine that ignores its PID is not (D59).
- **The ABP2 frame-size discovery**: the C++ reads 7 bytes of a 12-byte frame and mixes the second word's status byte into the temperature count, never checks either status byte, and can convert out-of-span counts into negative pressures the over-pressure logic accepts (D54).
- **The scale calibration's zero-divisor problem is solved with a separate `forbid_zero` flag rather than a narrower range**, because the negative half of the range is real (the shipped config has −1750.05) — a schema decision most migrations would get wrong (D52).
- **The C6 pin-budget finding with a full pin-count derivation** (23 exposed → 21 less USB → 15 less the module's 6 SDIO pins → 14 less the RGB LED), a named C6 map with strapping-pin justification per line, and the observation that the C6 vendor guide **contradicts its own J3 table** about whether the flash pins are broken out (board-pinouts.md).
- **The C++ contradicts itself about the backflush flush phase**: the valve is closed while the log says "flushing into drip tray" and the interlock whitelist says the valve may be open. The port resolves it toward the whitelist, and the C++'s alternative reading (isolate the group) is stated explicitly (D49).
- **A secret-handling doctrine built from property, not memory**: secrets are marked *in the schema*, and the log sink redacts them "by construction rather than by remembering"; the host tool's output is a status line only; `just flash` requires the operator to type `FLASH` and states data loss before writing; `check-secrets.py` runs in CI; the provisioning protocol replies `WIFI_SET` with no value and refuses to echo a malformed payload (architecture.md §6, tooling.md, SKILL.md §8).
- **`espflash write-bin` is documented as the fallback and is how the factory image is written in CI**, with an evidence line: a 2 571 412-byte ELF yields a 99 728-byte app image at 0x10000 (decision-record.md, verification-levels.md).
- **The honest negative results are stated rather than papered over**: multi-drop 1-Wire enumeration is not verified *and why that is acceptable*; the font metrics are a new input that makes all layout tests self-referential; the ESP32 and S3 board crates have never seen a compiler and this is "the fact most likely to be forgotten by the next reader"; `format_version: 2` is refused **by name and in full** because half-applying a newer document "is how a downgrade destroys a configuration" (HANDOFF.md, D58, parity-report.md).
- **A migration-path-specific rule most branches would miss**: parity scope excludes storage, partitions and OTA *by design*, and the ONLY bridge to the old firmware is export-from-old-UI → flash over USB → import — stated in the agent skill as "say exactly that in the user guide and nowhere else, because it is the whole procedure" (SKILL.md §9).
- **A "problem features" table with line-count estimates and options presented to the user** (P1–P9), each resolved by a dated user decision rather than by the author — an unusually explicit record of who decided what (inventory.md §10, task-list.md "Deferred and dropped").
- **Inert-by-design parameters are listed rather than quietly ignored** — `display.post_brew_timer_duration`, `hardware.relays.*.trigger_type`, the maintenance backflush reminder nag, and `hardware.sensor.nominal_resistance` are registered, readable, and marked inert, with a test that fails if a schema key is neither read nor listed (parity-report.md §5–6, `config_rt::NOT_READ_BY_THE_MACHINE`).
